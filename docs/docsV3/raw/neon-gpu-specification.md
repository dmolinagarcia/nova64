# Neon — GPU Specification

**Project:** DANI-65816
**Subsystem:** Neon (FPGA-B) — Graphics Processing Unit
**Revision:** 1.0 — consolidated
**Date:** 2026-08-14
**Supersedes:** *Neon Text Mode Specification*, *Neon Graphics Modes and Command Engine*

---

## 1. Scope and Intent

This document specifies the graphics half of Neon in full: display timing, the three video modes, the drawing engine, the command interface, the register map, and the resource budget. Section 21 gives worked usage scenarios from power-on through games.

The audio half (APU) is out of scope and shares only the device, the memory arbiter, and the register file base.

Three principles govern the design:

**Text mode must not depend on anything.** Mode 0 uses no SDRAM, no arbiter, no FIFO, and no inter-FPGA signalling. A console exists before the memory controller — the most defect-prone block in Neon — has been written, and is therefore available as the instrument for debugging everything else.

**The CPU must not draw.** The 65816 at 8 MHz can move about 1.6 MB/s through the aperture; a full 320×200 screen takes it 40 ms. The drawing engine does the same work in 0.3 ms. Every design decision that follows favours moving work off the CPU, culminating in the autonomous command lists of §14.3.

**Logic, not bandwidth, is the constraint.** With dedicated SDRAM, scanout consumes under 3% of memory bandwidth. What limits Neon is the 7,680 LUT and 32 EBR blocks of the iCE40 HX8K. Features are judged on LUT cost against what the blitter can already do.

## 2. Terminology

Defined at first use throughout; collected here for reference.

| Term | Definition |
|---|---|
| **Neon** | The combined graphics and audio processor implemented in FPGA-B. |
| **Cell** | One character position: a glyph code plus an attribute byte. |
| **Glyph** | The pixel pattern for one character code. |
| **EBR** | Embedded Block RAM — dual-port memory blocks inside the FPGA (512 bytes each), distinct from logic resources. |
| **LUT** | Look-Up Table — the unit of programmable logic in the FPGA. |
| **Aperture** | The 64 KB window in CPU bank `$FE` through which the 65816 reaches Neon. |
| **Scanout** | Reading display data and emitting pixels to the panel in real time. |
| **RGB-TTL** | Parallel digital video: separate colour bit lines plus pixel clock and syncs, at logic levels. |
| **Active area** | The panel region that displays image data, as opposed to blanking intervals. |
| **Border** | Panel active area not occupied by image data, filled with a solid colour. |
| **Ring buffer** | A buffer addressed modulo its size, so advancing a pointer rotates the contents without moving data. |
| **Blitter** | Hardware that fills, copies, and combines rectangular memory regions without CPU involvement. |
| **Command list** | A sequence of drawing commands in memory, executed autonomously by Neon. |
| **SDRAM bank** | One of four independent arrays inside the SDRAM device; accesses to different banks interleave without row-activation delay. |
| **Row activation** | The delay when SDRAM must open a new row before its data is accessible (~60 ns). |
| **Colour key** | A palette index designated transparent; pixels of that value are not written during a copy. |
| **Page flip** | Displaying one framebuffer while drawing into another, then exchanging them. |
| **Barrel shifter** | Logic that shifts a word by any amount in one cycle; required to place 1-bpp images at arbitrary horizontal positions. |
| **Clock enable** | A signal gating a register's update without gating its clock, used to derive a slower rate inside one clock domain. |
| **Service port** | The SPI channel from the RP2040 to Neon, reused after FPGA configuration as a control path (§15). |
| **Stride** | The byte distance between the start of one image row and the next; permits operating on a sub-rectangle of a larger image. |

## 4. Clocking

A single clock domain at **102.000 MHz**, generated by one PLL from the 12 MHz reference:

```
DIVR = 0, DIVF = 33, DIVQ = 2
Fout = 12 MHz × 34 / (1 × 2^2) = 102.000 MHz
```

The pixel stage advances on a clock enable asserted every second cycle, giving a **51.000 MHz** pixel rate. `PCLK` is emitted through a DDR output register, producing a clean panel clock with no combinational clock path and no divided-clock domain.

SDRAM runs at the full 102 MHz, exactly 2× the pixel rate.

Consequences:

1. **No clock-domain crossing anywhere in Neon.** No synchroniser FIFOs between scanout and memory. This eliminates an entire class of intermittent, hard-to-diagnose failure.
2. **The second PLL is unallocated** — available to audio, or held in reserve.
3. Refresh rate is 59.76 Hz.

> **Risk R-1.** 102 MHz is demanding for an iCE40 HX. SDRAM controllers in this range are documented on the family, but closure is unproven until synthesis. **Fallback:** run everything at 51 MHz single-rate, halving peak SDRAM bandwidth to 102 MB/s. All performance figures below halve and still exceed CPU-driven rendering by more than an order of magnitude. The architecture does not depend on 102 MHz; only the margins do.

## 6. Memory Architecture

Neon has two memories with a strict division of responsibility.

### 6.1 EBR — on-chip, dual-port, zero latency

Holds everything that must be reachable by the CPU without a wait state, and everything scanout needs at single-cycle latency.

| Structure | Size | Blocks | Used in |
|---|---|---|---|
| Text buffer | 8 KB | 16 | Mode 0 |
| Font | 4 KB | 8 | Mode 0 |
| Palette, 256 × 18-bit | 1 KB | 2 | All |
| Scanout line buffer, double | 1 KB | 2 | Modes 1, 2 |
| Blitter source/destination burst buffers | 1 KB | 2 | Modes 1, 2 |
| Command FIFO, 128 × 32-bit | 512 B | 1 | Modes 1, 2 |
| Cursor pattern | 512 B | 1 | All |
| **Total** | **16 KB** | **32** | |

**Fully allocated, zero margin.** This closes only because the tile engine and sprite engine were removed (§12.5).

Two reliefs are available and should be treated as insurance, not as slack:

- **Reduce the font to 128 glyphs** (2 KB — full ASCII plus box-drawing), freeing 4 blocks. Simplest, and should be a synthesis parameter from the start.
- **Multiplex the 16 text-buffer blocks into graphics use**, freeing 8 KB in graphics modes at the cost of address multiplexers, and destroying screen contents across a mode switch — acceptable, since returning to text mode implies a redraw.

**The font blocks must not be reclaimed under any scheme.** Their bitstream initialisation is what permits printing before any software exists (§21.1); reusing them would destroy it.

> **Open item O-3.** Decide the relief strategy once the blitter's real EBR demand is known from synthesis, not before.

### 6.2 SDRAM — off-chip, high bandwidth, write-only from the CPU

Holds framebuffers, image assets, and command lists. Peak 204 MB/s at 102 MHz on a 16-bit bus. Row activation costs ~20 clocks per 512-word row (~4% on sequential access); auto-refresh ~0.2%. Sequential throughput is ~185 MB/s; budget **~150 MB/s effective** for mixed workloads.

| Consumer | Mode 2a | Mode 1 |
|---|---|---|
| Scanout | 3.8 MB/s | 4.6 MB/s |
| Hardware cursor | 0.1 MB/s | 0.1 MB/s |
| Audio DMA | 0.7 MB/s | 0.7 MB/s |
| CPU aperture writes, worst case | 1.6 MB/s | 1.6 MB/s |
| **Available to the drawing engine** | **~144 MB/s** | **~143 MB/s** |

Scanout consumes under 3% of the memory system. **Memory bandwidth is not a design constraint for Neon.**

Source and destination of a copy should be placed in **different SDRAM banks** where possible, so the controller interleaves them and avoids a row activation on every alternation. This is a memory-layout convention for the kernel and asset loader; the hardware does not enforce it.

## 7. CPU Access Model

This section states a restriction that shapes all software using Neon. It is stated early because it is easy to design around and expensive to discover late.

### 7.1 Mode 0 — full read/write

Text buffer, font, and palette are in dual-port EBR. Port A serves scanout, port B serves the CPU. At 102 MHz fabric against 8 MHz PHI2, every CPU access — **read or write** — completes within its bus cycle. No wait states, no FIFO, no shadow copy.

### 7.2 Modes 1 and 2 — write-only

SDRAM reads carry row-activation latency, and Neon cannot stretch PHI2 to cover it: doing so requires a wait line to FPGA-A, and the architecture has eliminated the inter-FPGA link.

**The graphics VRAM aperture is therefore write-only.** Writes are absorbed by a 32-entry FIFO and retired by the arbiter; the CPU never waits. Reads return `$FF` and set `STATUS.READ_FAULT`.

The register file at `$FE:FF00` remains fully readable in all modes — it is in fabric registers, not SDRAM.

### 7.3 `PEEK` — diagnostic read path

Where a read is genuinely required:

1. Write the 24-bit SDRAM address to `PEEK_ADDR`.
2. Poll `STATUS.PEEK_READY`.
3. Read `PEEK_DATA`.

Roughly 20 CPU cycles per byte. **Intended for debugging, screen capture, and nothing in a hot path.**

### 7.4 What this means in practice

Asset flow is one-way: microSD → system memory → aperture → VRAM. Once the drawing engine is running, the CPU has no reason to read the framebuffer.

The one consequence that reaches software design is that **a GUI cannot implement save-under by reading the screen into system memory**. It can still implement save-under, because the *blitter* reads VRAM without restriction — the save-under buffer simply lives in VRAM and is moved by a `COPY_RECT`. See §21.4.

> **Open item O-4.** If a signal line from FPGA-B to FPGA-A is added for interrupts (§18), one additional line would permit PHI2 stretching and make the aperture fully readable. These two lines should be evaluated as a pair, not decided separately.

## 8. Aperture Map

Bank `$FE`, 64 KB. Access remains subject to the MMU's `VRAM_SEL` protection in FPGA-A; this document does not alter the protection model.

| Range | Size | Mode 0 | Modes 1 / 2 |
|---|---|---|---|
| `$FE:0000`–`$FE:1FFF` | 8 KB | Text buffer (R/W) | VRAM write window |
| `$FE:2000`–`$FE:2FFF` | 4 KB | Font (R/W) | VRAM write window |
| `$FE:3000`–`$FE:7FFF` | 20 KB | unmapped | VRAM write window |
| `$FE:8000`–`$FE:83FF` | 1 KB | Palette (R/W) | Palette (write-only) |
| `$FE:8400`–`$FE:FEFF` | — | unmapped | unmapped |
| `$FE:FF00`–`$FE:FFFF` | 256 B | Registers (R/W) | Registers (R/W) |

In graphics modes, `$FE:0000`–`$FE:7FFF` is a **32 KB window** into SDRAM at byte offset `VRAM_PAGE × 32768`. The window is a power of two so page arithmetic is a shift.

> This supersedes an earlier claim that the Mode 2a framebuffer "fits in a single aperture page". It spans two. The point is now moot: with the blitter drawing, the CPU walks the framebuffer only during asset upload, where paging costs one register write per 32 KB.

## 9. Mode 0 — Text

### 9.1 Geometry

| Parameter | Value | Derivation |
|---|---|---|
| Cell size | **8 × 16 px** | 1024 / 8 = 128 exactly |
| Columns | **128** | |
| Rows | **32** | 32 × 16 = 512 lines |
| Total cells | **4096** | 2¹², exactly 12-bit addressable |
| Text area | 1024 × 512 px | panel lines 44–555 |
| Border | 44 lines top, 44 lines bottom | (600 − 512) / 2 |

The 8×16 cell is the standard VGA text cell. Any existing 8×16 VGA font is usable unmodified; glyph row lookup is a 4-bit shift; and **descenders are not truncated** — a 15-line cell would clip `g j p q y` and force a bespoke font.

4096 cells being an exact power of two is what makes the ring-buffer scroll of §9.4 free: the address wrap is a bit mask, not a comparator.

### 9.2 Character generation

No line buffer is required; generation is fully real-time. Per cell the pipeline needs one text-buffer read and one font read every 8 pixel clocks — a factor of 8 of slack at 51 MHz.

For panel active line `L`, 44 ≤ L ≤ 555:

```
text_row   = (L - 44) >> 4
glyph_row  = (L - 44) & 15

cell_index = (TEXT_START + text_row * 128 + column) & 0x0FFF
cell_addr  = cell_index << 1

code       = text_buffer[cell_addr]
attribute  = text_buffer[cell_addr + 1]
glyph_bits = font[(code << 4) | glyph_row]
```

Each of the 8 bits selects between foreground and background palette entries, MSB leftmost. The pipeline is 3 stages deep; cell fetch begins 3 clocks before the first active pixel, absorbed in the back porch.

Outside the text area and during horizontal blanking, the output is `BORDER_COLOR`.

### 9.3 Cell format

Two bytes, little-endian, naturally aligned:

```
Byte 0 (even):  code[7:0]        — glyph index
Byte 1 (odd):   bg[3:0] fg[3:0]  — bits 7:4 background, bits 3:0 foreground
```

Both are indices into the first 16 palette entries.

A 65816 in 16-bit accumulator mode writes a complete cell with one `STA`. This is **one instruction but two bus cycles** — the data bus is 8 bits. The saving is instruction overhead, not bus traffic.

Full-screen fill: 8,192 bytes, ≈ **5 ms** at 8 MHz with an unrolled loop.

> **Deferred.** No per-character blink attribute. The VGA approach reallocates attribute bit 7, cutting the background palette to 8 entries; retaining full 16/16 colour is judged more valuable. If added later it should be a global mode bit that reinterprets bit 7, not a silent format change.

### 9.4 Scrolling

The text buffer is a ring of 4096 cells. `TEXT_START` is the cell index displayed at the top-left corner.

To scroll up one line: add 128 to `TEXT_START` modulo 4096, then clear the 128 cells of the newly exposed bottom row.

| | Bytes moved | Time at 8 MHz |
|---|---|---|
| Naive block move | 8192 | ~5 ms |
| `TEXT_START` + clear one row | 256 | **~160 µs** |

Because the ring wraps at exactly 4096 cells, software needs no wrap special case — the hardware masks the index.

### 9.5 Font

256 glyphs × 16 bytes. Byte *n* of a glyph is pixel row *n*, MSB leftmost, `1` = foreground. Address: `(code << 4) | row`.

**Two-tier residency:**

- **Default font initialised in the bitstream.** The system prints from the instant FPGA configuration completes — before the microSD is mounted, before a kernel exists, before the 65816 leaves reset. This is not a convenience; it is the only way to get boot diagnostics onto the screen.
- **Replaceable at runtime** by writing `$FE:2000`–`$FE:2FFF`.

> Writing the font outside vertical blanking may produce a single-frame artefact on the glyph row being fetched at that instant. Harmless, but a full font load should occur during vblank.

### 9.6 Power-on state

The text buffer EBR is likewise initialised at synthesis: every cell set to code `$20` with attribute `$0F` (light grey on black), and the palette to the standard 16-colour CGA/EGA set. The screen is blank and correctly coloured at power-on rather than showing random EBR contents.

## 10. Mode 1 — Hires Monochrome

| Parameter | Value |
|---|---|
| Resolution | **1024 × 600** — native, no replication, square pixels |
| Depth | 1 bpp |
| Framebuffer | 128 B/line × 600 = **76,800 B** |
| Bit order | MSB leftmost |
| Colours | `MONO_FG`, `MONO_BG` — two palette indices |
| Border | none, full panel |
| Scanout | 4.6 MB/s |

This is the GUI mode. Full panel resolution at 1:1 is what makes readable text and precise window furniture possible.

**The expensive part of Mode 1 is arbitrary-alignment blitting**, not the framebuffer. Placing an image at any horizontal position in a packed 1-bpp buffer requires shifting each source word by 0–15 bits, merging across word boundaries, and masking both edges. Estimated **~400 LUT**. It is not optional: a GUI that can only draw on 16-pixel boundaries is not a GUI.

## 11. Mode 2 — Multicolour

Two sub-modes differing only in replication factor and stride. Both are 8 bpp with the 256-entry palette.

| | **Mode 2a** | **Mode 2b** |
|---|---|---|
| Logical resolution | 320 × 200 | 512 × 300 |
| Replication | 3 × 3 | 2 × 2 |
| Displayed area | 960 × 600 | **1024 × 600 — exact** |
| Horizontal border | 32 px each side | none |
| Framebuffer | **64,000 B** | 153,600 B |
| Scanout | 3.8 MB/s | 9.2 MB/s |
| Double-buffered | 128 KB | 300 KB |

**Mode 2a** is the recommended default for games: familiar geometry, and pixels that are exactly square because the panel's are.

**Mode 2b** fills the panel with no border, costing only memory and bandwidth — both abundant. Better wherever black side bars would be objectionable.

Both use identical logic; the sub-mode is a register field controlling the replication counters and line stride. Supporting 2b costs approximately nothing.

## 12. Drawing Engine

### 12.1 Operations

| Operation | Description |
|---|---|
| `FILL_RECT` | Solid colour fill |
| `FILL_PATTERN` | Fill with the 8×8 pattern register |
| `COPY_RECT` | Opaque rectangular copy, overlap-safe (direction chosen automatically) |
| `COPY_KEYED` | Copy skipping pixels equal to the colour key |
| `COPY_TILED` | Copy with the source wrapped modulo its dimensions — texture fill |
| `COPY_EXPAND` | 1-bpp source expanded to two colours — glyphs and icons into Mode 2 |
| `DRAW_LINE` | Bresenham, arbitrary endpoints |
| `DRAW_HLINE` / `DRAW_VLINE` | Optimised axis-aligned cases |

All respect the clip rectangle set by `SET_CLIP`. All take independent source and destination strides, so any operation may address a sub-rectangle of a larger image.

> `COPY_TILED` is the resolution of "apply texture": filling a region by repeating a bitmap, in the QuickDraw and Amiga-blitter sense. **Perspective-correct 3D texture mapping is out of scope and not implementable on this device** — it needs a per-pixel divide, and the iCE40 has neither hardware multipliers nor the logic budget to build them.

### 12.2 Cost per full-screen operation, Mode 2a (64,000 B)

| Operation | Traffic | Time | vs. 65816 |
|---|---|---|---|
| `FILL_RECT` | 64 KB write | **0.31 ms** | 129× |
| `COPY_RECT` | 64 KB read + 64 KB write | **~1.0 ms** | 40× |
| `COPY_KEYED` | read src + read dst + write dst | **~1.5 ms** | 27× |
| `DRAW_LINE` | ~1 px/clock | 1024 px in 10 µs | — |

Reference: the 65816 needs ~40 ms for a full-screen rewrite through the aperture.

### 12.3 Frame budget

One frame at 59.76 Hz is 16.7 ms. After scanout, cursor, audio, and CPU traffic, roughly **15.5 ms** remains for drawing — about 50 full-screen fills, or 15 full-screen opaque copies, or 10 keyed copies.

### 12.4 Hardware cursor

A single 16×16 or 32×32, 2-bpp cursor composited at scanout, in all three modes.

In Mode 0 it is rendered by swapping foreground and background palette indices for the affected pixels of the cell at `CURSOR_POS`, with shape and blink selected by `CURSOR_CTRL`. It consumes no buffer storage and requires no save/restore by software.

In Modes 1 and 2 the pattern is held in EBR and positioned by pixel coordinate.

`CURSOR_POS` in Mode 0 is a **buffer-absolute** cell index, so it scrolls with the text it is attached to. A terminal wanting the cursor pinned to the last visible row updates it on scroll — one register write.

### 12.5 Removed: hardware tile mode and sprite engine

Both were specified in an earlier draft and are deliberately **not** implemented. The reasoning is recorded because it will otherwise be re-litigated.

**Tile mode.** The blitter redraws a full 320×200 tilemap — 260 tiles of 16×16 — in **~1.3 ms**, under 8% of a frame. It can therefore rebuild the entire tiled background every frame from scratch and leave 92% for everything else, with pixel-smooth scrolling free by offsetting destination coordinates. A hardware tile engine would cost ~800 LUT to accelerate this, and would fragment rendering into two incompatible paths.

**Sprite engine.** Blitting 32 masked 16×16 sprites costs ~8 KB of keyed transfer — **~0.12 ms**, 0.7% of a frame. Hardware sprites exist to avoid save/restore of background in systems that cannot afford to redraw. With double buffering and 32 MB of SDRAM, that problem does not arise: each frame is drawn fresh into the back buffer.

Combined saving: **~1,650 LUT**, about 21% of the device. This is what takes Neon from 95% occupancy — not routable once audio grows — to 76%.

What is given up: sprites composited at scanout cost no framebuffer bandwidth and cannot be erased by drawing, which simplifies certain effects. What is gained: one rendering model, and the logic budget to fit the blitter, command processor, and audio on one device.

The hardware cursor is retained because a GUI pointer must track the mouse independently of the rendering loop.

## 13. Double Buffering

`DISPLAY_BASE` holds the SDRAM address of the framebuffer being scanned out; `DRAW_BASE` holds the one the engine writes. Both are 24-bit byte addresses.

`SWAP_BUFFERS` exchanges them **at the next vertical blanking interval**, never mid-frame, so a partially drawn frame is never displayed. The command completes immediately; the exchange is latched and applied by the timing generator.

Cost in memory is trivial — 128 KB for Mode 2a against 32 MB available. Double buffering should be considered the default for anything animated.

## 14. Command Interface

Three layers, each usable independently. Layer 3 is the one that renders without CPU intervention; layers 1 and 2 exist because they are needed first during bring-up.

### 14.1 Layer 1 — Register-driven

Parameters written to the blitter registers (§17), execution triggered by writing `BLIT_CTRL.GO`, completion detected by polling `STATUS.BLIT_BUSY`.

Simple, verifiable, and requiring no FIFO or decoder. This is how the blitter is tested in isolation at stage N1. **It is not intended for production use** — the CPU is occupied for the duration of every operation.

### 14.2 Layer 2 — Command FIFO

The CPU writes 32-bit command words to `CMD_PORT`, a single aperture address. Neon buffers them in a 128-entry EBR FIFO and executes them in order, asynchronously.

Software checks `CMD_FIFO_FREE` before writing a command's worth of words. The FIFO does not fill under realistic load: the CPU produces roughly 1.6 MB/s while a full-screen fill is 5 words in and 0.31 ms of work.

This alone decouples the CPU from drawing, and is sufficient for a GUI.

### 14.3 Layer 3 — Command lists in SDRAM

`EXEC_LIST` redirects the command processor to fetch its instruction stream from SDRAM instead of from the FIFO. Lists may contain any drawing command plus flow control:

| Command | Effect |
|---|---|
| `JUMP addr` | Continue at `addr` |
| `CALL addr` / `RET` | One level of subroutine nesting |
| `WAIT_VBLANK` | Suspend until the next vertical blanking interval |
| `WAIT_LINE n` | Suspend until panel line `n` — raster-synchronised effects |
| `SWAP_BUFFERS` | Exchange front and back buffers at the next vblank |
| `SET_PALETTE i, rgb` | Palette write; may be mid-frame after `WAIT_LINE` |
| `SET_CLIP` | Set the clip rectangle for subsequent operations |
| `SIGNAL n` | Raise an interrupt to the CPU with tag `n` |
| `END` | Return to FIFO execution |

**This is the autonomous rendering mode.** A game builds its display list once, terminates it with `SWAP_BUFFERS` and `JUMP` back to the start, and the CPU is then free: Neon renders every frame indefinitely until the list is modified. Per-frame CPU work reduces to patching coordinates inside an existing list — a handful of 16-bit stores.

The model is the ANTIC display list and the Amiga Copper, generalised to include the blitter.

### 14.4 Self-modifying lists

Because the CPU can write into a list while Neon executes it, moving an object is a store to a parameter word of an existing `COPY_KEYED`. This is the intended usage pattern, not an abuse.

Two mechanisms guard against reading a half-updated command:

- **`CMD_CTRL.LIST_LOCK`.** The engine finishes its current command, then stalls before fetching the next. The kernel patches, clears the lock, and execution resumes. Holding the lock across a vblank costs a frame, so patches must be short.
- **`SIGNAL` plus the frame gap.** The list ends with `SIGNAL n` before `WAIT_VBLANK`. The CPU patches in the interval between the signal and the next frame's drawing. No lock, no stall, but the patch must complete inside the remaining frame time.

The second is preferred for steady-state animation; the first for structural changes to the list.

### 14.5 Command word format

Word 0:

```
bits 31:24  opcode
bits 23:16  flags (clip enable, key enable, direction, ...)
bits 15:0   count of parameter words following
```

Parameters follow as 32-bit words, packing two 16-bit coordinates each where applicable. `FILL_RECT` is 5 words total; `COPY_KEYED` is 7.

Explicit word count was chosen over fixed length per opcode so that an unknown opcode can be skipped rather than desynchronising the stream. This matters when gateware and kernel versions drift during development.

## 15. Service Port

The RP2040 configures FPGA-B over SPI. **After configuration completes, the same four pins are reused as a control channel into Neon.** This costs no additional pins and approximately 200 LUT.

The service port reaches:

- the register file,
- the text buffer, font, and palette in EBR,
- SDRAM, through the same arbiter port used by the CPU aperture.

Three things this makes possible, none otherwise available:

**Display before the CPU exists.** The RP2040 writes boot progress to the text buffer while FPGA-A is still being configured and the 65816 is still in reset. Without this, the first thing on screen would have to wait for working CPU, working MMU, and working BIOS — which is precisely when a display is most needed.

**A debug channel independent of the CPU bus.** If the 65816 hangs, the RP2040 can still read Neon's registers and write to the screen. During bring-up this is the difference between a diagnosable failure and a dark panel.

**Bulk asset loading that bypasses the CPU.** At 20 MHz SPI the port sustains ~2.5 MB/s from microSD into SDRAM, against the CPU's ~1.3 MB/s through the aperture — and it costs the 65816 nothing. For a 1.6 MB level this is roughly 0.6 s instead of 1.2 s of fully occupied CPU.

> **Open item O-11.** SDRAM write access from the service port shares the arbiter with the CPU FIFO and could instead be limited to EBR only, saving perhaps 100 LUT and some arbiter complexity. The bulk-load benefit is real but is not required by any milestone. Decide at N2.

## 16. Interrupts

Neon raises three interrupt sources, individually enabled in `IRQ_EN` and cleared by writing 1 to the corresponding bit of `IRQ_STATUS`:

| Bit | Source |
|---|---|
| 0 | Vertical blank |
| 1 | Raster line compare against `RASTER_CMP` |
| 2 | `SIGNAL` command executed; tag readable in `IRQ_TAG` |

> **Open item O-4.** This requires one signal line from FPGA-B to the 65816 `IRQB`, which was not in the earlier FPGA-B pin budget (~99 of ~107 usable I/O). Routing it through FPGA-A would allow masking but reintroduces an inter-FPGA signal the architecture had eliminated. As noted in §7.4, if a line is added anyway, adding a second for PHI2 stretching — which would make the aperture readable — should be evaluated at the same time.

Until this is resolved, software must poll `STATUS.VBLANK`. All scenarios in §21 are written to work either way.

## 17. Register Map

Base `$FE:FF00`. All registers byte-wide. Reserved bits read zero, write zero.

### Global

| Offset | Name | Access | Description |

## 20. Verification Criteria, Stage N0

1. Panel syncs and displays a stable image at 59.76 Hz with no tearing or jitter.
2. At power-on, before any CPU activity, the screen shows a blank field in the default background colour with correct borders.
3. The RP2040, via the service port, writes glyphs that appear at the correct positions.
4. Reading back the text buffer through the aperture returns exactly what was written.
5. Advancing `TEXT_START` by 128 scrolls the display by exactly one row with no artefacts.
6. The hardware cursor appears at `CURSOR_POS` in the selected shape, blinking at the selected rate.
7. A font written through the aperture takes effect on the following frame.
8. `RASTER` tracks the display; the vblank flag sets once per frame.

Criteria 1–3 and 8 are achievable **before the 65816 is populated**. This is the intended E0 bring-up path.

## 21. Usage Scenarios

This section traces how Neon is actually used, from power-on to games. Code is illustrative rather than final, and assumes the Calypsi C and ca65 conventions in use elsewhere in the project.

### 21.1 Power-on and boot

**Nothing configures Neon for display. It is already displaying.**

This is the single most useful property of the design and it is worth being explicit about why. The text buffer, font, and palette are EBR contents initialised from the bitstream. The moment FPGA-B's configuration completes and `CDONE` rises, the timing generator begins scanning and the panel receives valid video — 128 × 32 spaces, light grey on black, correct borders. There is no register to write, no mode to select, no PLL to wait for beyond the FPGA's own configuration.

Boot sequence:

| Step | Actor | Screen state |
|---|---|---|
| 1 | RP2040 boots from its W25Q16 | dark |
| 2 | RP2040 sequences power rails | dark |
| 3 | RP2040 configures FPGA-B over SPI | dark |
| 4 | `CDONE` rises; timing generator starts; backlight enabled | **blank text screen** |
| 5 | RP2040 switches SPI to service-port mode | blank |
| 6 | RP2040 writes a banner | **"DANI-65816 — RP2040 OK"** |
| 7 | RP2040 configures FPGA-A | *"FPGA-A configuring..."* |
| 8 | RP2040 mounts microSD | *"microSD: 8 GB"* |
| 9 | RP2040 loads BIOS into system SRAM | *"BIOS 12 KB loaded"* |
| 10 | RP2040 releases 65816 reset | *"Starting CPU..."* |

Every step from 6 onward is visible. If step 7 or 9 fails, the failure is on the screen rather than inferred from a dark panel — which is the entire justification for the service port.

The RP2040 writes a character by pushing a service-port transaction: address within the text buffer, then the two bytes of the cell. A `neon_puts()` in the RP2040 firmware is perhaps thirty lines.

**Neon is the only subsystem on this board that is useful before anything else works.** That ordering was deliberate and should be preserved as the design evolves.

### 21.2 BIOS

The BIOS inherits a working display and needs **no initialisation whatsoever**. It does not probe Neon, does not set a mode, does not load a font. It writes bytes to `$FE:0000` and characters appear.

The BIOS should read `NEON_ID` once and expect `$4E`, purely to distinguish "no Neon fitted" from "Neon fitted", and continue in either case.

A complete `putchar`:

```asm
; Direct page:
;   CURSOR  .word   ; cell index, 0..4095
;   ATTR    .byte   ; colour attribute
; Text buffer at $FE:0000, 2 bytes per cell.

putchar:
        cmp #$0A                ; newline?
        beq do_newline
        rep #$20                ; 16-bit accumulator
        lda CURSOR
        asl                     ; cell index -> byte offset
        tax
        sep #$20                ; 8-bit accumulator
        lda CHAR
        sta $FE0000,x           ; glyph code
        lda ATTR
        sta $FE0001,x           ; attribute
        rep #$20
        inc CURSOR
        lda CURSOR
        and #$0FFF              ; wrap the ring
        sta CURSOR
        sep #$20
        ; fall through to cursor update
update_cursor:
        rep #$20
        lda CURSOR
        sta $FEFF12             ; CURSOR_POS: low then high, latches on high
        sep #$20
        rts
```

Two details are load-bearing:

- `sta $FE0000,x` is absolute-long indexed. The bank byte is in the instruction, so no bank register manipulation is needed and the BIOS may run from any bank.
- The 16-bit store to `$FEFF12` writes the low byte then the high byte. Because `CURSOR_POS` latches on the high-byte write, the update is atomic with no explicit sequencing in software.

Scrolling is a pointer move, not a memory move:

```asm
scroll_up:
        rep #$20
        lda TEXT_START_SHADOW
        clc
        adc #128                ; one row of cells
        and #$0FFF
        sta TEXT_START_SHADOW
        sta $FEFF10             ; TEXT_START
        ; clear the newly exposed bottom row: 128 cells
        clc
        adc #(31*128)           ; index of the bottom row
        and #$0FFF
        asl
        tax
        ldy #128
        lda #$0F20              ; space, light grey on black
clear_loop:
        sta $FE0000,x
        inx
        inx
        dey
        bne clear_loop
        sep #$20
        rts
```

256 bytes written instead of 8,192 moved: **~160 µs instead of ~5 ms**. On a console that scrolls constantly during boot, this is the difference between scrolling being visible and being free.

### 21.3 Operating system, text mode

**The hardware mechanism is identical to the BIOS.** The same stores to the same addresses. Nothing about Neon changes between BIOS and kernel, and the surmise that the answer would be the same is correct.

Four things differ, all in software layering:

**Driver wrapping.** Per the project's driver architecture, the console becomes a kernel-internal driver implementing the fixed five-function interface, reached by userspace through a file descriptor on `/dev/tty`. `write()` becomes a loop over `putchar`. Neon does not know or care.

**MMU mapping.** Bank `$FE` is privileged and not user-mappable. Only the kernel-side driver touches it; user processes reach the console through the syscall path. This is unchanged from the existing protection model.

**Custom fonts.** The kernel may load a font from microSD into `$FE:2000`–`$FE:2FFF`. It should do so with `STATUS.VBLANK` set, to avoid a one-frame artefact on the glyph row being fetched.

**Timing.** The kernel can take its display tick from the vblank interrupt rather than polling — subject to O-4.

The following is worth stating because it is a genuine constraint on kernel design: **the console occupies EBR that graphics modes need.** Switching to a graphics mode may, depending on the resolution of O-3, destroy the text buffer contents. The tty driver must therefore treat the screen as lost across a mode switch and be able to repaint from its own scrollback in system memory. This is normal for a virtual-console design but must be built in from the start, not retrofitted.

### 21.4 Graphics mode: GUI and windows

> **Does the CPU write everything into VRAM? No — and this is the central point of Neon's design.** The CPU writes *commands*. The blitter writes VRAM. A CPU that painted windows byte by byte would spend 40 ms per full screen and have nothing left for the system it is supposed to be running.

Mode 1 (1024 × 600, 1 bpp) is the GUI mode: full panel resolution, square pixels, 75 KB per buffer.

**Resources held in VRAM, loaded once at boot:**

| Asset | Contents |
|---|---|
| Glyph atlas | 1-bpp bitmaps for the UI font, packed horizontally, with a width table in system memory |
| Icon atlas | 1-bpp or keyed 8-bpp icons |
| Patterns | 8×8 fills for window backgrounds, desktop texture, disabled states |
| Save-under pool | Scratch region for occluded regions |

#### Who loads a window's content

The question divides, and the two halves have opposite answers.

**Assets** — icons, bitmaps, the UI font — are pixel data. The CPU uploads them to VRAM once, through the aperture, at boot or at application load. Alternatively the service port (§15) loads them straight from microSD at roughly twice the rate and at no cost to the CPU. Once resident they stay resident, and everything afterwards refers to them by source rectangle.

**Generated content** — text, charts, plots, anything the application computes — never becomes pixel data in system memory at all. The application emits commands. Drawing a line of text is not "loading pixels"; it is one `COPY_EXPAND` per glyph from a font atlas already in VRAM.

**The CPU therefore writes pixels exactly once per asset, and never again.** Any design in which the CPU is building bitmaps in system memory and pushing them to VRAM per frame has taken a wrong turn, and will run at the 1.3 MB/s aperture rate rather than the blitter's 100 MB/s.

**Drawing a window** is a short command sequence. Nothing here touches the CPU beyond emitting the words:

```
SET_CLIP    x, y, x+w, y+h
FILL_RECT   x,   y,   w,   h,   COLOR_FACE      ; body
FILL_RECT   x,   y,   w,   20,  COLOR_TITLE     ; title bar
DRAW_HLINE  x,   y,   w,   COLOR_EDGE           ; frame
DRAW_HLINE  x,   y+h, w,   COLOR_SHADOW
DRAW_VLINE  x,   y,   h,   COLOR_EDGE
DRAW_VLINE  x+w, y,   h,   COLOR_SHADOW
COPY_KEYED  icon_atlas -> x+4, y+2, 16, 16      ; window icon
COPY_EXPAND glyph_atlas -> ...                  ; title text, one per glyph
```

Text rendering is one `COPY_EXPAND` per glyph, source-rectangle selected from the atlas by the width table. A 40-character title is 40 commands — 280 words, about 1,120 bytes through the aperture, roughly 700 µs of CPU. For a title drawn once on window creation this is acceptable. For a text editor repainting a full screen of text, the display-list approach of §21.5 applies equally and should be used.

#### A window is not a rectangle that moves

This is the single most important thing to understand about the GUI, and getting it wrong leads to a design that cannot work.

**There are no windows in VRAM.** There is one flat framebuffer containing pixels. A window is a structure in system memory — coordinates, title, widget list, z-order — and what appears on screen is pixels that something painted there. **No association exists in hardware between those pixels and the window that produced them.**

The consequence is immediate: if window A sits over window B and A is moved away, B's pixels **are not underneath**. They were overwritten when A was drawn. They are gone.

So moving a window with a single `COPY_RECT` — which does work, and costs ~0.3 ms for 400 × 300 at 1 bpp — leaves two problems behind:

- **The exposed region** where the window was. Something has to repaint whatever should be visible there.
- **What the window now covers.** If another window occupied the destination, those pixels no longer exist and cannot be recovered by moving the window away again.

A straight `COPY_RECT` drag is therefore correct only over a uniform background. As soon as windows overlap, the robust path is to repaint from the structures in system memory.

This is why every windowing system has a **damage model**: dirty rectangles, z-order traversal, and repaint from application state. It is not incidental complexity — it follows directly from having a flat framebuffer.

#### Neon makes the damage model cheap

Repainting an entire window costs roughly **1 ms**. That buys a significant simplification: the compositor can skip precise damage-region arithmetic — the most defect-prone part of any window manager — and simply repaint the full rectangle of every window intersecting the dirty area, back to front.

**This is the recommended first implementation.** Optimise to precise regions only if a specific case demands it. On machines of this class that trade was not available; here it is.

#### Alternative: per-window buffers with compositing

Each window owns a buffer in VRAM; the framebuffer is produced by compositing them in z-order. This removes the damage problem entirely — occluded content still exists, so moving a window is a recomposite rather than a repaint.

| | Flat framebuffer | Per-window buffers |
|---|---|---|
| Occluded content | Destroyed | Preserved |
| Move a window | Repaint from state | Recomposite |
| Memory | 75 KB | 75 KB + ~15 KB per window |
| Per-frame cost | Zero when idle | Full recomposite |
| Software complexity | Damage tracking | Buffer management |
| Gateware | As specified | Additional composition path |

It is affordable: 32 MB of VRAM and ~143 MB/s make per-window buffers and a full recomposite entirely practical, which is not true of most systems this size.

**It is nonetheless deferred.** It is materially more gateware and more software, and it should not be attempted before the flat model is working. Recorded as O-18 so the option is not lost.

**Save-under works, despite the write-only aperture.** This is worth spelling out because the constraint of §7 appears at first to forbid it. The restriction is on *the CPU* reading VRAM. The blitter reads VRAM without restriction. So:

```
COPY_RECT   screen(x,y,w,h) -> saveunder_pool    ; before opening a menu
...
COPY_RECT   saveunder_pool -> screen(x,y,w,h)    ; on closing it
```

The saved region never leaves VRAM and the CPU never sees it. Save-under is a bounded special case — a menu over a known rectangle, restored before anything else can be drawn there — and does not substitute for the damage model above.

The only thing genuinely impossible is the CPU *inspecting* pixel data, needed for screen capture and colour-picker tools. Both can use `PEEK` and tolerate its slowness.

### 21.5 Graphics mode: games

This is where command lists (§14.3) earn their logic cost. The worked example is a side-scrolling platformer at Mode 2a, 320 × 200, 256 colours, double buffered.

#### The wrong approach, and why

The obvious method is a tilemap in system memory, redrawn per frame as one `COPY_RECT` per tile. The blitter handles it easily: 260 tiles of 16 × 16 is ~1.3 ms.

**But the CPU cannot feed it.** 260 commands × 7 words × 4 bytes = 7,280 bytes through the aperture at ~1.3 MB/s = **5.6 ms per frame**, a third of the frame budget spent purely on issuing commands. The bottleneck moved from drawing to command bandwidth.

#### The right approach: pre-rendered level, one command

SDRAM is 32 MB. Use it.

**At level load,** render the entire level background once into a large SDRAM buffer. A level 8,192 pixels wide at 200 high, 8 bpp, is 1.64 MB — five percent of memory. Ten levels could be resident simultaneously. The rendering is done once, by tile blits, and its cost is irrelevant because it happens during a load screen.

**Per frame, scrolling the background is one command:**

```
COPY_RECT   src = level_buffer + scroll_x,  src_stride = 8192
            dst = back_buffer,              dst_stride = 320
            w = 320, h = 200
```

One `COPY_RECT` with a source stride of 8,192 windows a 320-wide viewport out of the level. Scrolling is a change to `scroll_x` — **one 16-bit store**. Cost: ~1.0 ms of blitter time, seven command words.

Parallax is a second such command from a second buffer with an independent `scroll_x`, drawn first, with the foreground layer keyed over it.

#### Characters

Sprite frames live in a VRAM atlas, loaded at level start. Each character is one `COPY_KEYED` selecting a source rectangle from the atlas.

Twenty characters at 32 × 32 is 20 × 1,024 = 20,480 pixels of keyed transfer, roughly **0.3 ms**.

#### The frame display list

Built once, at level start, and then executed forever:

```
frame_list:
        WAIT_VBLANK
        SWAP_BUFFERS
        COPY_RECT    background   ; parameters patched each frame
        COPY_KEYED   sprite_00    ; \
        COPY_KEYED   sprite_01    ;  } parameters patched each frame
        ...                       ; /
        COPY_KEYED   sprite_19
        COPY_EXPAND  hud_text     ; score, lives
        SIGNAL       1            ; frame drawn; safe to patch
        JUMP         frame_list
```

The CPU writes `LIST_BASE` and sets `CMD_CTRL.LIST_RUN` once. **From that point Neon renders continuously with no further CPU involvement.**

#### Per-frame CPU cost

Game logic updates positions in its own structures, then patches the list:

| Patch | Words |
|---|---|
| Background `scroll_x` | 1 |
| 20 sprite destinations (x, y packed) | 20 |
| 20 sprite sources (animation frame) | 20 |
| HUD, when it changes | ~4 |
| **Total** | **~45 words = 180 bytes** |

At ~1.3 MB/s that is **~140 µs per frame, under 1% of the frame budget.** The remaining 99% belongs to game logic — physics, collision, AI, input — which is what the 65816 should be doing.

Synchronisation uses the `SIGNAL 1` at the end of the list: the CPU patches in the interval between the signal and the next `WAIT_VBLANK`. No lock is needed and the engine never stalls.

#### Frame budget summary

| Item | Time |
|---|---|
| Background copy | ~1.0 ms |
| 20 keyed sprites | ~0.3 ms |
| HUD | ~0.1 ms |
| **Blitter total** | **~1.4 ms of 15.5 ms** |
| CPU list patching | ~0.14 ms of 16.7 ms |

**Roughly 9% of the drawing budget and 1% of the CPU.** The headroom is enough for a second parallax layer, a full-screen effect, or several times as many characters.

### 21.6 What each scenario demonstrates

| Scenario | Mechanism | CPU cost |
|---|---|---|
| Boot | Bitstream-initialised EBR; service port | none — no CPU exists |
| BIOS | Direct stores to `$FE:0000` | trivial; no init |
| OS text | Identical to BIOS, wrapped in a driver | trivial |
| GUI | Command FIFO; blitter draws | ~1 ms per window |
| Games | SDRAM display list; blitter draws | ~140 µs per frame |

The progression is deliberate: each layer is available without the one above it, so a failure in the command processor still leaves a working console, and a failure in SDRAM still leaves a working boot display.
