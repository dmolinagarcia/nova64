# Persistent storage — microSD
> where it connects · boot · normal use

A single slot, two owners at different times. It's also the only boot path: the dedicated BIOS flash was removed from the design.

- G.1 — Connection: the slot hangs off an **SN74CBTLV3257** mux between the RP2040 and Helium's SPI-SD controller, with a handoff handshake.
  NOTE: **Why the card is switched rather than simply left with the EC**, which is the cheaper arrangement and was examined as a way of recovering pins on Helium. Swap is what forbids it: the page evictor writes a frame out and the fault path reads one back, so the card needs a direct route into Helium, and giving it to the EC instead puts a microcontroller and its link in the middle of the page-fault path. The mux, the handshake and Helium's own SPI-SD controller are what that costs, and they were accepted on those grounds rather than on pin count (→ [L.16](sec_l#l16)).
- G.2 — At boot: the RP2040 owns the SD — it reads `BIOS.BIN` from FAT and preloads it into the pinned SRAM zone (steps 5–6 of Fig. 3). It then switches the mux to Helium before releasing reset.
- G.3 — In normal use: the 65816 accesses it through Helium's SPI-SD via the kernel's block driver. The BIOS mounts FAT read-only to load `KERNEL.BIN`; the OS adds write support and the user filesystem.
  NOTE: Read-only in the BIOS is deliberate: less code before a kernel exists, and no way for a half-built boot path to damage the card it booted from.
- G.4 — Card contents: `/BIOS.BIN` · `/KERNEL.BIN` · user tree (programs, data) · future reserve for swap.
- G.5 — Recovery: the RP2040 can reclaim the SD over USB at any time — update BIOS/kernel without removing the card.
- G.6 — **The card needs a register block in Helium, and it is the peripheral block [Q22](sec_q#q22) has been holding space for.** Everything above describes a path from the slot to memory; none of it is reachable until the 65816 has a control surface for it, and the SPI-SD controller of [B.2](sec_b#b2) is that block's first tenant. It sits behind its own 256-byte wall in `$FF:0000`–`$FF:7FFF` like every other block in the bank, registers 16 bits and accessed with `M=0`, following [sheet M](sec_m)'s conventions — **and it costs no pins**: the decode is a widening of a comparator that already exists on the CPU bus ([M.3](sec_m#m3)). The pins it does cost are the SPI-SD lines themselves, and those are already open and blocking as [Q8](sec_q#q8). Its base address is unassigned along with the rest of the map, so the register table below is written as offsets (→ [Q22](sec_q#q22), [Q40](sec_q#q40)).
- G.7 — **Two data paths, both present, sharing one set of registers.** The block exposes a **FIFO** — the CPU reads 512 bytes through `SD_DATA` — and a **DMA engine** that deposits blocks straight into SDRAM as a client of Helium's arbiter. This is not indecision: they arrive at different stages and answer different needs.
  NOTE: **Why the FIFO is not enough on its own.** At 8 MHz a copy loop costs 12–15 cycles per 16-bit word, so moving a 512-byte block through the accumulator is ~3,500 cycles — **roughly 440 µs with the CPU at 100 %**, against the ~164 µs the SPI link itself takes at 25 MHz. The transport costs more than the medium, and it costs it in the one resource the machine has least of. Worse, a FIFO-only design **retracts [G.1](sec_g#g1)**: the whole argument for the mux, the handshake and a controller inside Helium was that the page evictor and the fault path need a direct route between the card and a frame. If every byte has to pass through the CPU anyway, the card could have stayed with the EC and Helium could have kept the pins.
  NOTE: **Why the FIFO exists at all, then.** It touches neither the arbiter nor the cache, so it is a page of gateware rather than a subsystem, and it is what makes [E6](sec_p#e6) and [P5.j](sec_p#p5j) — mount FAT, load `KERNEL.BIN`, list a directory — reachable before the DMA engine is written or the coherence rule of [G.9](sec_g#g9) is implemented. Bring-up uses it; demand paging cannot.
- G.8 — **The DMA engine addresses physical memory, never virtual.** It is not behind the MMU: no TLB lookup, no walker, no permission check. The destination is a frame number plus an offset, and the kernel — which owns the page tables — translates and pins the buffer before writing the registers. A 512-byte block never straddles a 2 KB frame provided the destination is block-aligned, which the block driver enforces rather than the hardware.
  NOTE: This is also the protection argument. An engine that took a virtual address would need an ASID, a walker port and a permission check to avoid becoming a way for a process to write outside its own address space; one that takes a physical frame is unreachable from user code by construction, because the registers live in bank `$FF` ([M.1](sec_m#m1)).
- G.9 — **Coherence: the read direction needs the mirror of [L.16](sec_l#l16), and it is the sharper of the two.** The cache sits in front of the SDRAM, so an engine writing a frame behind it leaves the CPU's view stale — and a *dirty* line for that frame is worse than stale, because it will be written back on top of the DMA'd data at some arbitrary later moment. **The rule is: invalidate the destination frame, then start the transfer.** Not flush — the contents about to be overwritten are worthless, and writing them out first wastes an SDRAM burst to no purpose. [M.9](sec_m#m9) already covers a destination in the pinned region, which is non-cacheable by requirement; this is the SDRAM case. The command is `CACHE_INVAL_FRAME` and it did not previously exist (→ [sheet M](sec_m)'s register map).
  NOTE: The two rules are worth stating together, because they are asymmetric and the asymmetry is the part that gets misremembered. **Card ← memory: flush the frame, then write** ([L.16](sec_l#l16)). **Card → memory: invalidate the frame, then read.** Both fail silently, both fail only under memory pressure, and [F.7](sec_f#f7)'s line-equals-frame sizing makes each of them a single tag lookup.
- G.10 — **Completion is a `BUSY` bit and an interrupt, and the transfer must not stall PHI2.** [M.6](sec_m#m6) forbids stalling the clock for something the kernel could poll, on the grounds that microseconds of scheduler jitter on every page eviction is not payable; an SD transfer is hundreds of microseconds, an order of magnitude further past the line. Unlike a cache flush, though, it should not be polled either: the block driver blocks a process for the duration anyway, so completion raises an IRQ through Helium's PIC and the scheduler runs somebody else. `BUSY` remains readable for the BIOS and for bring-up, where no scheduler exists to hand the time to.
  TEST: a DMA read of 64 blocks completes while the CPU runs a counter loop throughout, and PHI2 never stops.
  NOTE: Gateware rule, the same one [M.6](sec_m#m6) states for asynchronous commands: `BUSY` must read 1 on the first read after the triggering write, never lag, and a trigger written while `BUSY` is set is ignored — it neither queues nor aborts.
  NOTE: Which is also the argument for the interrupt over the poll: a block is ~164 µs of SPI, so a driver that spins burns a quantum watching a bit where one that blocks gives the time back ([X.25](sec_x#x25) argues the same one tier down).
- G.11 — **Card initialisation is software, not a state machine.** `SD_CMD`, `SD_ARG_L`/`SD_ARG_H` and `SD_RESP` expose a raw SD command, and the CMD0 · CMD8 · ACMD41 · CMD58 sequence, the voltage negotiation and the SDHC-versus-SDSC determination are all driven by the kernel through them. Helium's gateware does the SPI shifting and the block engine, nothing above that — which is [B.2](sec_b#b2)'s rule that intelligence lives in software applied to the one peripheral most tempting to violate it for.
  TEST: a cold card the EC has never touched, brought from power-on to `SD_CARD.initialised` by the 65816 alone.
  NOTE: It is also not optional. [G.2](sec_g#g2) hands Helium a card the EC has already initialised, so the fast path can skip the sequence — but after a [G.5](sec_g#g5) reclaim, or a card swap, or any resume in which the EC touched the slot, the 65816 has to be able to bring a cold card up with no EC involvement. The addressing mode matters beyond initialisation: SDSC takes a byte address and SDHC a block number, and `SD_CARD` publishes which, so the driver does not have to guess.
  NOTE: `SD_CTRL` bit 3 is part of the same story: a cold card runs at ≤ 400 kHz until it has answered, then moves to full speed. A state machine would have hidden that transition; software owning it makes the change one register write.

## Register map — the storage block. Offsets from a base still to be assigned within `$FF:0000`–`$FF:7FFF` (→ [Q22](sec_q#q22)).

| Offset | Name | Access | Meaning |
|---|---|---|---|
| `+$00` | SD_LBA_L | read/write | Sector address, bits [15:0] |
| `+$02` | SD_LBA_H | read/write | Sector address, bits [31:16] |
| `+$04` | SD_DST_FRAME | read/write | Destination physical frame, DMA only |
| `+$06` | SD_DST_OFF | read/write | Byte offset within the frame, DMA only. Block-aligned |
| `+$08` | SD_DMA_READ | write | Card → memory. Argument: block count. **The destination frame must have been invalidated first** ([G.9](sec_g#g9)). Asynchronous |
| `+$0A` | SD_DMA_WRITE | write | Memory → card. Argument: block count. **The source frame must have been flushed first** ([L.16](sec_l#l16)). Asynchronous |
| `+$0C` | SD_PIO_READ | write | Card → `SD_DATA`. Argument: block count. Asynchronous |
| `+$0E` | SD_PIO_WRITE | write | `SD_DATA` → card. Argument: block count. Asynchronous |
| `+$10` | SD_DATA | read/write | FIFO port for the PIO path. `SD_STATUS` carries the empty and full flags |
| `+$12` | SD_STATUS | read | Bit 0 `BUSY` · 1 `FIFO_EMPTY` · 2 `FIFO_FULL` · 3 `ERR_CRC` · 4 `ERR_TIMEOUT` · 5 `ERR_ARB` · 6 `NO_CARD` · 7 `IRQ_PENDING` |
| `+$14` | SD_CARD | read | Bit 0 card present · 1 initialised · 2 `SDHC` — block addressing rather than byte · 3 write-protected · 15:4 reserved |
| `+$16` | SD_CTRL | write | Bit 0 IRQ enable · 1 clear `IRQ_PENDING` · 2 clear error bits · 3 SPI clock divisor select — the initialisation sequence runs at ≤ 400 kHz, transfers at full speed |
| `+$18` | SD_CMD | write | Raw SD command index. Argument: the index; the argument registers must be loaded first |
| `+$1A` | SD_ARG_L | read/write | Raw command argument, bits [15:0] |
| `+$1C` | SD_ARG_H | read/write | Raw command argument, bits [31:16] |
| `+$1E` | SD_RESP | read | Response to the last raw command. Successive reads walk a multi-byte R3/R7 response |
