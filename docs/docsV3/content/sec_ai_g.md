# Persistent storage — microSD
> where it connects · boot · normal use

A single slot, **one owner, permanently**. And it is no longer the boot path: the machine boots with the slot empty, which is the largest thing [D60](sec_ai_q#d60) changed about this sheet.

- G.1 — Connection: the slot wires **directly and permanently to Helium's SPI-SD controller**. Six pins, one owner. **There is no multiplexer, no ownership handshake, and no SD driver in the EC's firmware** — the EC has no connection to the card at all ([D60](sec_ai_q#d60)).
  NOTE: **The argument for a direct route into Helium is unchanged and is now the only route.** Swap is what demands it: the page evictor writes a frame out and the fault path reads one back, so putting a microcontroller and its link in the middle of the page-fault path was never acceptable (→ [L.16](sec_ai_l#l16)). What has gone is the *other* half — the EC needed the card at boot to read `BIOS.BIN`, and that is what the switching, the '3257 and the handshake existed to serve. **With the bitstreams and `bios.bin` in EC flash ([D1.21](sec_ai_d1#d121)) that need is deleted, and the sharing machinery goes with it**: one analogue switch, six EC pins, an atomicity requirement and a state machine, none of which now has anything to do.
  NOTE: This is the one place in the document where a peripheral stopped being handed over and simply became somebody's — and [H.1](sec_ai_h#h1) lost its worked example in the process. **Nothing on this board is now shared between two masters at any time**, which is a stronger statement than the one that rule started as.
- G.2 — **At boot the card does nothing, and that is the point.** `bios.bin` reaches system RAM from EC flash over the mailbox before `RESB` is released ([D1.22](sec_ai_d1#d122)); the card is not read, not initialised, and not required to be present. The 65816 discovers it after it is already running, through the block driver, like any other peripheral.
  NOTE: **A missing or unreadable card is therefore not a boot failure but a message on the screen.** It is discovered by the running system rather than by the EC, and Neon is configured long before that point ([D1.23](sec_ai_d1#d123)), so it can be *reported* rather than merely signalled by a machine that stops. Under the old arrangement an empty slot was a dead machine with a blink code.
  NOTE: **The card's format is specified and it is not FAT.** The system volume is NVFS ([sheet Y2](sec_ai_y2)) in an MBR partition of type `0x7F`, whose first eight blocks are reserved ([Y2.5](sec_ai_y2#y25)). **The reservation survives the change of boot path but loses its original tenant**: it was there so a boot image could sit at the front of the partition where an EC with almost no filesystem code could find it. No EC ever reads it now. It is worth keeping for the update images of [D1.24](sec_ai_d1#d124), which are found by the 65816 with a real filesystem underneath it (→ [Q130](sec_ai_q#q130)).
- G.3 — In normal use: the 65816 accesses it through Helium's SPI-SD via the kernel's block driver. **The BIOS mounts NVFS read-only to load `KERNEL.BIN`** — a minimal reader that neither verifies checksums nor replays the journal, which [Y2.20](sec_ai_y2#y220) deliberately makes possible by putting both of those in the read-only feature mask; the OS mounts it read-write behind [sheet Y1](sec_ai_y1), and adds ext2 for anything that arrived from a host ([sheet Y3](sec_ai_y3)).
  NOTE: Read-only in the BIOS is deliberate: less code before a kernel exists, and no way for a half-built boot path to damage the card it booted from. **The format enforces it rather than trusting it**: a read-only mounter that meets a dirty volume or a non-empty journal must refuse, so a BIOS cannot quietly read a card that needs recovery ([Y2.20](sec_ai_y2#y220)).
- G.4 — Card contents: `/KERNEL.BIN` · user tree (programs, data) · future reserve for swap · and the **update images** of [D1.24](sec_ai_d1#d124) when one is being applied. All of it in the NVFS partition.
  NOTE: **`/BIOS.BIN` is no longer among them, and this is the visible face of the change.** The BIOS is in EC flash and is delivered to SRAM before the CPU runs ([D1.22](sec_ai_d1#d122)); a copy on the card would be a file nothing reads. **What replaces it is the opposite flow** — a *new* `bios.bin` arriving on the card from a host, which the running system pushes into EC flash over the mailbox rather than the EC pulling it off the card ([D1.24](sec_ai_d1#d124)).
- G.5 — **Recovery no longer runs through this slot, and the sheet is better for it.** The RP2354B cannot reclaim the card — it has no wires to it — so the reclaim path, its atomicity requirement and the question of what happens to a mounted volume underneath a running kernel all disappear. **Updating the BIOS is now [D1.24](sec_ai_d1#d124)'s A/B path** and updating the kernel is a file copy; neither needs the card taken away from anybody.
  NOTE: What the old G.5 was really buying was *a way in that does not need the card removed from the machine*, and that need is met better elsewhere: the console UART reaches a monitor that can read and write memory directly ([D3.14](sec_ai_d3#d314)), and SWD reaches the EC against blank flash with the machine unpowered ([D1.13](sec_ai_d1#d113)). **Neither existed when this item was written.**
- G.6 — **The card needs a register block in Helium, and it is the peripheral block [Q22](sec_ai_q#q22) has been holding space for.** Everything above describes a path from the slot to memory; none of it is reachable until the 65816 has a control surface for it, and the SPI-SD controller of [B.2](sec_ai_b#b2) is that block's first tenant. It sits behind its own 256-byte wall in `$FF:0000`–`$FF:7FFF` like every other block in the bank, registers 16 bits and accessed with `M=0`, following [sheet M](sec_ai_m)'s conventions — **and it costs no pins**: the decode is a widening of a comparator that already exists on the CPU bus ([M.3](sec_ai_m#m3)). The pins it does cost are the SPI-SD lines themselves, and those are already open and blocking as [Q8](sec_ai_q#q8). Its base address is unassigned along with the rest of the map, so the register table below is written as offsets (→ [Q22](sec_ai_q#q22), [Q40](sec_ai_q#q40)).
- G.7 — **Two data paths, both present, sharing one set of registers.** The block exposes a **FIFO** — the CPU reads 512 bytes through `SD_DATA` — and a **DMA engine** that deposits blocks straight into SDRAM as a client of Helium's arbiter. This is not indecision: they arrive at different stages and answer different needs.
  NOTE: **Why the FIFO is not enough on its own.** At 8 MHz a copy loop costs 12–15 cycles per 16-bit word, so moving a 512-byte block through the accumulator is ~3,500 cycles — **roughly 440 µs with the CPU at 100 %**, against the ~164 µs the SPI link itself takes at 25 MHz. The transport costs more than the medium, and it costs it in the one resource the machine has least of. Worse, a FIFO-only design **retracts [G.1](sec_ai_g#g1)**: the whole argument for wiring the card to Helium and building a controller inside it was that the page evictor and the fault path need a direct route between the card and a frame. If every byte has to pass through the CPU anyway, the six pins bought nothing that a link to the EC would not have bought more cheaply.
  NOTE: **Why the FIFO exists at all, then.** It touches neither the arbiter nor the cache, so it is a page of gateware rather than a subsystem, and it is what makes [E6](sec_ai_p#e6) and [P5.j](sec_ai_p#p5j) — mount the volume, load `KERNEL.BIN`, list a directory — reachable before the DMA engine is written or the coherence rule of [G.9](sec_ai_g#g9) is implemented. Bring-up uses it; demand paging cannot.
- G.8 — **The DMA engine addresses physical memory, never virtual.** It is not behind the MMU: no TLB lookup, no walker, no permission check. The destination is a frame number plus an offset, and the kernel — which owns the page tables — translates and pins the buffer before writing the registers. A 512-byte block never straddles a 2 KB frame provided the destination is block-aligned, which the block driver enforces rather than the hardware.
  NOTE: This is also the protection argument. An engine that took a virtual address would need an ASID, a walker port and a permission check to avoid becoming a way for a process to write outside its own address space; one that takes a physical frame is unreachable from user code by construction, because the registers live in bank `$FF` ([M.1](sec_ai_m#m1)).
- G.9 — **Coherence: the read direction needs the mirror of [L.16](sec_ai_l#l16), and it is the sharper of the two.** The cache sits in front of the SDRAM, so an engine writing a frame behind it leaves the CPU's view stale — and a *dirty* line for that frame is worse than stale, because it will be written back on top of the DMA'd data at some arbitrary later moment. **The rule is: invalidate the destination frame, then start the transfer.** Not flush — the contents about to be overwritten are worthless, and writing them out first wastes an SDRAM burst to no purpose. [M.9](sec_ai_m#m9) already covers a destination in the pinned region, which is non-cacheable by requirement; this is the SDRAM case. The command is `CACHE_INVAL_FRAME` and it did not previously exist (→ [sheet M](sec_ai_m)'s register map).
  NOTE: The two rules are worth stating together, because they are asymmetric and the asymmetry is the part that gets misremembered. **Card ← memory: flush the frame, then write** ([L.16](sec_ai_l#l16)). **Card → memory: invalidate the frame, then read.** Both fail silently, both fail only under memory pressure, and [F.7](sec_ai_f#f7)'s line-equals-frame sizing makes each of them a single tag lookup.
- G.10 — **Completion is a `BUSY` bit and an interrupt, and the transfer must not stall PHI2.** [M.6](sec_ai_m#m6) forbids stalling the clock for something the kernel could poll, on the grounds that microseconds of scheduler jitter on every page eviction is not payable; an SD transfer is hundreds of microseconds, an order of magnitude further past the line. Unlike a cache flush, though, it should not be polled either: the block driver blocks a process for the duration anyway, so completion raises an IRQ through Helium's PIC and the scheduler runs somebody else. `BUSY` remains readable for the BIOS and for bring-up, where no scheduler exists to hand the time to.
  TEST: a DMA read of 64 blocks completes while the CPU runs a counter loop throughout, and PHI2 never stops.
  NOTE: Gateware rule, the same one [M.6](sec_ai_m#m6) states for asynchronous commands: `BUSY` must read 1 on the first read after the triggering write, never lag, and a trigger written while `BUSY` is set is ignored — it neither queues nor aborts.
  NOTE: Which is also the argument for the interrupt over the poll: a block is ~164 µs of SPI, so a driver that spins burns a quantum watching a bit where one that blocks gives the time back ([X.25](sec_ai_x#x25) argues the same one tier down).
- G.11 — **Card initialisation is software, not a state machine.** `SD_CMD`, `SD_ARG_L`/`SD_ARG_H` and `SD_RESP` expose a raw SD command, and the CMD0 · CMD8 · ACMD41 · CMD58 sequence, the voltage negotiation and the SDHC-versus-SDSC determination are all driven by the kernel through them. Helium's gateware does the SPI shifting and the block engine, nothing above that — which is [B.2](sec_ai_b#b2)'s rule that intelligence lives in software applied to the one peripheral most tempting to violate it for.
  TEST: a cold card the EC has never touched, brought from power-on to `SD_CARD.initialised` by the 65816 alone.
  NOTE: **It is also not optional, and it is now the only case rather than the fallback one.** The old text allowed a fast path in which Helium inherited a card the EC had already initialised; **no card is ever initialised by anything but the 65816 now** ([G.1](sec_ai_g#g1)), so the sequence runs on every cold boot, every card swap and every resume, and there is no second path to keep working. That removes a class of bug rather than adding work: the rarely-exercised branch was the one that would have rotted. The addressing mode matters beyond initialisation: SDSC takes a byte address and SDHC a block number, and `SD_CARD` publishes which, so the driver does not have to guess.
  NOTE: **[Sheet Y2](sec_ai_y2) makes one request of this block and it is short: the natural transfer unit is four consecutive sectors — 2048 bytes, one NVFS block, one MMU page — into a 2048-byte-aligned buffer.** `SD_DMA_READ` and `SD_DMA_WRITE` already take a block count, so satisfying it costs nothing but issuing a multi-block command rather than four single-sector ones; **four transfers with per-command overhead is measurably worse than one burst, and the difference multiplies through every figure in [Y2.23](sec_ai_y2#y223)'s cost model.** It is much cheaper to design in before this map is frozen than to add afterwards ([Y2.24](sec_ai_y2#y224)).
  NOTE: `SD_CTRL` bit 3 is part of the same story: a cold card runs at ≤ 400 kHz until it has answered, then moves to full speed. A state machine would have hidden that transition; software owning it makes the change one register write.

## Register map — the storage block. Offsets from a base still to be assigned within `$FF:0000`–`$FF:7FFF` (→ [Q22](sec_ai_q#q22)).

| Offset | Name | Access | Meaning |
|---|---|---|---|
| `+$00` | SD_LBA_L | read/write | Sector address, bits [15:0] |
| `+$02` | SD_LBA_H | read/write | Sector address, bits [31:16] |
| `+$04` | SD_DST_FRAME | read/write | Destination physical frame, DMA only |
| `+$06` | SD_DST_OFF | read/write | Byte offset within the frame, DMA only. Block-aligned |
| `+$08` | SD_DMA_READ | write | Card → memory. Argument: block count. **The destination frame must have been invalidated first** ([G.9](sec_ai_g#g9)). Asynchronous |
| `+$0A` | SD_DMA_WRITE | write | Memory → card. Argument: block count. **The source frame must have been flushed first** ([L.16](sec_ai_l#l16)). Asynchronous |
| `+$0C` | SD_PIO_READ | write | Card → `SD_DATA`. Argument: block count. Asynchronous |
| `+$0E` | SD_PIO_WRITE | write | `SD_DATA` → card. Argument: block count. Asynchronous |
| `+$10` | SD_DATA | read/write | FIFO port for the PIO path. `SD_STATUS` carries the empty and full flags |
| `+$12` | SD_STATUS | read | Bit 0 `BUSY` · 1 `FIFO_EMPTY` · 2 `FIFO_FULL` · 3 `ERR_CRC` · 4 `ERR_TIMEOUT` · 5 `ERR_ARB` · 6 `NO_CARD` · 7 `IRQ_PENDING` |
| `+$14` | SD_CARD | read | Bit 0 card present · 1 initialised · 2 `SDHC` — block addressing rather than byte · 3 write-protected · 15:4 reserved |
| `+$16` | SD_CTRL | write | Bit 0 IRQ enable · 1 clear `IRQ_PENDING` · 2 clear error bits · 3 SPI clock divisor select — the initialisation sequence runs at ≤ 400 kHz, transfers at full speed |
| `+$18` | SD_CMD | write | Raw SD command index. Argument: the index; the argument registers must be loaded first |
| `+$1A` | SD_ARG_L | read/write | Raw command argument, bits [15:0] |
| `+$1C` | SD_ARG_H | read/write | Raw command argument, bits [31:16] |
| `+$1E` | SD_RESP | read | Response to the last raw command. Successive reads walk a multi-byte R3/R7 response |
