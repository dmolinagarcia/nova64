# RP2354B — embedded controller
> boot · FPGA programming · USB and HID · the ways back in

It's the laptop's "management microcontroller": it handles everything that happens before a live CPU exists, and stays on watch afterward. **The part is now a single RP2354B in QFN-80**, and that change is the subject of [D1.8](sec_ai_d1#d18) onward, along with the USB topology, the on-board hub and the three recovery paths that replace the one this design used to rely on.

- D1.1 — Triple role: **programmer** (bitstreams, BIOS, its own firmware), **bootstrapper** (full sequence in Fig. 3), and permanent **embedded controller**. **Its 2 MB of flash is in the package**, and it is the board's only non-volatile storage — no longer merely the only *mandatory* one, since [D60](sec_ai_q#d60) put the gateware and the BIOS in it and took the microSD out of the boot path entirely ([D1.21](sec_ai_d1#d121)).
  NOTE: **Which makes that flash the most valuable single object in the machine.** It holds the gateware for all three FPGAs, the system firmware and the EC's own image; a board with a blank one is inert in a way no other single failure makes it. Everything about [D1.13](sec_ai_d1#d113)'s recovery tiers, [D1.19](sec_ai_d1#d119)'s prohibition on the OTP bits, and the A/B scheme of [D1.24](sec_ai_d1#d124) is written on that basis rather than on convenience.
  NOTE: **The flash moving inside the package removes a part from the always-on domain and removes a net from the board**, and it costs the recovery argument that used to sit here. The old one was that a bad write to the external W25Q16 took the whole boot with it, but `BOOTSEL` over USB answered whatever the flash held and took a UF2, so a bricked EC needed no programmer and no header. **That path is gone** — [D1.9](sec_ai_d1#d19) commits the USB port to host mode and it cannot be borrowed back — and it is replaced by three paths that do not involve USB at all ([D1.13](sec_ai_d1#d113)).
- D1.2 — **Boot is a state machine, and the microSD is not in it** (Fig. 3, states tabulated in [D1.22](sec_ai_d1#d122)): button → rails in REV C order → Neon configured → Helium configured → FPGA-C if populated → `bios.bin` written into SRAM from EC flash → `RESB`↑ → `$FFFC` vector → runtime. **Every byte the machine needs before the CPU exists comes out of the EC's own package.**
  NOTE: **Configure Neon first, and the rest of the sequence becomes visible while it happens.** Neon's `CDONE` is the point at which the panel starts showing a correct blank screen with no register written; from there the EC switches its SPI into service-port mode ([T.46](sec_ai_t#t46)) and writes each subsequent step to the text buffer — Helium configuring, the BIOS transferring, the CPU released. **A failure in any of those steps is then on the panel instead of being inferred from a dark one**, which is the whole argument for the service port and the reason the configuration order is a requirement rather than a preference (→ [T.53](sec_ai_t#t53), [T.64](sec_ai_t#t64)).
  NOTE: **The circular dependency that used to sit here is gone rather than solved.** The old sequence had the EC holding the microSD past FPGA configuration because `bios.bin` was on the card, which meant the card had to be released to Helium *after* Helium was alive but *before* the CPU ran — a one-way handoff wedged between two other orderings, with no way to retry it. **With the BIOS in EC flash there is no ordering constraint left to get wrong**, and [G.1](sec_ai_g#g1) drops the mux that implemented it.
- D1.3 — Debugging: a debug port into FPGA-A (Helium) — live read/write of system memory, a free "ICE" for the kernel. The EC does not master the bus to do it: it drives a **debug agent inside Helium** over a dedicated SPI chip select, and that block issues the accesses as a peer of the CPU port. Specified in [sheet R](sec_ai_r).
  NOTE: **That was one half of the debug story and the other half used to be missing.** The EC can halt and inspect the whole machine; nothing could halt or inspect the EC, and by [D1.7](sec_ai_d1#d17) its firmware holds the 10-second watchdog and the shutdown state machine — the parts whose misbehaviour looks like a hung kernel or a corrupt filesystem rather than like a firmware bug. **It is closed, and the thing that closes it is no longer a header.** `SWCLK`, `SWDIO` and the console UART are now carried by an **integrated probe on a chassis USB-C port** — an on-board RP2040 running `debugprobe`, specified in [sheet D2](sec_ai_d2) — so SWD is the *daily* programming path ([D1.13](sec_ai_d1#d113)) with no external tool, no cable to the inside of the machine, and nothing to open.
- D1.4 — Console: **a UART, and it is the EC's only console.** The USB-CDC console the earlier arrangement carried is gone with the device-mode port ([D1.9](sec_ai_d1#d19)); the on-board probe that programs the EC bridges this UART to the host over the same USB-C cable ([D2.21](sec_ai_d2#d221)), so the cable count is one. It's the terminal for the monitor (E2) and for development work throughout.
  NOTE: It is **no longer the only console, and no longer the first one.** Neon's text mode reaches the panel at [E1.7](sec_ai_p#e17), before Helium's UART exists and before the CPU runs at all, and the EC drives it over the service port with no bus in the picture ([T.64](sec_ai_t#t64)). The two are complementary rather than redundant: the serial line survives a dead panel and carries a host debugger, the screen survives a dead CPU and needs no PC attached.
- D1.5 — HID host: **the native USB controller in host mode, behind an on-board hub** — USB keyboard and mouse (PS/2 and matrix removed). It powers the downstream ports on demand and translates HID → events to the kernel over the EC channel.
  NOTE: **The hub is part of the machine, not an accessory the user supplies**, and it is now an IC on the board rather than something plugged into one port ([D1.10](sec_ai_d1#d110)). A portable computer needs more than one socket without a dongle, and a known-good on-board hub also removes a variability source during bring-up.
  NOTE: **The channel those events ride on is written, and it is [sheet D3](sec_ai_d3).** [Sheet H](sec_ai_h) named its endpoints and [sheet S](sec_ai_s) settled the power traffic; what was missing was the transport itself, and the mailbox now carries `HID_EVENT` in one direction and `HID_STATE` in the other, with **flow control that matters here specifically** — a 65816 at 8 MHz servicing IRQs can fall behind a burst of keystrokes, and `IN_SPACE` is what makes the EC throttle rather than overrun it ([D3.9](sec_ai_d3#d39), [D3.11](sec_ai_d3#d311)).
- D1.6 — Its own pin budget nearly failed too, and was rescued the same way the FPGA's was. Straight onto GPIO the EC needed roughly 38 pins against 30 available; an **MCP23017 I2C expander** absorbed everything with no timing requirement — the three CDONE lines, the charger's STAT and PG, the fuel gauge's alert, and the enables for the 1.2V rail, the panel and the host boost — bringing it to 28 of 30.
  NOTE: The pattern had appeared twice: both Helium and the EC ran out of pins, and both were saved by moving slow signals onto a cheaper transport — the keyboard matrix onto USB HID, the enables and status lines onto I2C. **Expect it a third time**, and [sheet X](sec_ai_x) is where it happened.
  NOTE: **The expander is retired, and this is the clearest thing the part change bought.** QFN-80 gives **48 GPIO** against the 30 that forced the expander, which absorbs REV C's per-rail `EN` and `PG` ([sheet C](sec_ai_c)), the two Helium handshake pins, and the hub's reset line with room left — and it removes the question of which power domain the expander itself lives in, which was open and awkward because an expander must sit on AON to drive an enable at all while its outputs cross into the switched domain ([Q41](sec_ai_q#q41) closes on this). One constraint disappears with it: PIO-USB's requirement that `D+` and `D−` sit on two consecutive GPIOs was a `pico-pio-usb` restriction, and there is no PIO-USB any more.
- D1.7 — **EC in operation, and this is no longer a sketch.** The button (short press ordered, ~4 s forced, `QON` for the hardware floor), the gauge and charger readout at 1 Hz, the telemetry push into Helium, and a shutdown that stays graceful with the OS hung — all specified in [sheet S](sec_ai_s), which also closes what used to be the EC↔kernel protocol question.
  NOTE: What the EC now owns that it did not before: **it is the only thing that can cut a rail**, and it holds the 10-second watchdog that decides when a kernel has stopped answering. That makes its firmware state machine part of the machine's data-integrity story, not just its housekeeping.

## The part — what changed, and what it deletes rather than adds.

- D1.8 — **One RP2354B, QFN-80, A4 stepping**, and the three things it removes are worth more than the pin count on its own. **48 GPIO** removes the pressure that motivated both the expander and, in an earlier arrangement, a second microcontroller. **2 MB of flash in the package** removes a component from the always-on domain and the net that went with it. And a **hardware USB host controller** removes the bit-banged PIO stack from the critical path — the silicon handles hub enumeration, the `PRE` packets Low Speed devices need, and bulk transfers, none of which anybody wants to debug in software.
  NOTE: **Confirm the stepping from the package marking on the parts as received, not from the distributor's part number.** RP2354 never shipped as A2, but the marking is the only thing that settles it (→ [Q104](sec_ai_q#q104)). Every GPIO assignment must also be validated against the function-mux table before capture, which is not the same exercise as counting pins (→ [Q105](sec_ai_q#q105)).
- D1.9 — **The native controller is assigned to host mode, and that assignment is one-way.** The USB-A receptacles source VBUS as a host, so attaching a PC would need an A-to-A cable with two 5 V supplies opposing each other: **`BOOTSEL` over USB is not structurally available, not merely unsupported.** Recovery is therefore restructured into three tiers that touch no USB port at all ([D1.13](sec_ai_d1#d113)), and the debug console is a UART ([D1.4](sec_ai_d1#d14)) rather than a second USB device.
  NOTE: **The USB-C connector carries power only** — VBUS and the two CC lines into the CH224K, with `D+`/`D−` unconnected. Which also settles [C.11](sec_ai_c#c11)'s warning by construction rather than by discipline: the CH224K cannot be tempted onto the data lines because there are none on that connector.
  NOTE: The alternative arrangements were examined and rejected. **Native as device with PIO as host** preserves drag-and-drop programming but puts the hub, the Low Speed `PRE` handling and the bulk transfers on the most fragile protocol path in the most fragile implementation. **Native as host with PIO as device** for a CDC console is defensible and is held as a fallback if a USB console ever proves necessary — it would *not* restore `BOOTSEL`, which needs the native controller in device mode. **A USB role mux** would restore it, at the cost of a part in the differential path, a connector and VBUS interlock logic, to recover a capability three independent tiers already cover.

## USB topology — one Full Speed bus, shared.

- D1.10 — **The hub's upstream port is Full Speed, and that is specification-mandated rather than a compromise.** It gets no answer to its Hi-Speed chirp from a Full Speed host, so it reverts to Full Speed and behaves as a pure repeater with the transaction translator bypassed — exactly what happens when a USB 2.0 hub is plugged into a USB 1.1 port. Everything downstream shares 12 Mbps; a Full Speed hub is a repeater and not a switch, so downstream traffic is retransmitted to every enabled port and only the device matching the token's address answers.
  NOTE: **Low Speed devices behind a hub need the host to emit a `PRE` packet before each transaction.** It is supported in silicon here, and it is historically the most fragile path in this family's host stack. **Verify it early, with a real keyboard** (→ [Q102](sec_ai_q#q102)).
  NOTE: **The on-board hub consumes the single supported hub level, and in a portable computer a user will plug another one in.** The tier limit has to be raised and multi-level handling verified rather than assumed, and if cascading proves unreliable the fallback is stated now: **detect a downstream hub during enumeration and refuse it with a message on the console**, rather than failing silently (→ [Q103](sec_ai_q#q103)).
- D1.11 — **`JP-BYPASS` puts a series jumper on `D+`/`D−` ahead of the hub with an alternate route straight to the first receptacle, and its value is entirely diagnostic.** At 12 Mbps a jumper costs nothing in signal integrity. What it buys is the difference between *"does the host stack work at all"* and *"does the hub work"* — **without it, a board that enumerates nothing tells you nothing about which of the two is at fault.** Three-pin header with a shunt, or two 0 Ω pads with one populated (→ [Q106](sec_ai_q#q106)).
- D1.12 — **There are no debug headers left to mislabel, and the risk moved rather than disappeared.** [Sheet D2](sec_ai_d2) replaces `J-DBG` with an integrated probe and `J-QSPI` with a test-pad footprint, so what needs silkscreen now is the **tier-3 pad order beside the package** and the **debug USB-C, told apart from the charging one** ([D2.24](sec_ai_d2#d224)). Transposing `SWCLK` and `SWDIO` still costs hours; it is now a schematic error rather than a wiring one ([D2.11](sec_ai_d2#d211)).

## Programming and recovery — three tiers, none of which touches the EC's own USB.

| Tier | Path | Interface | Writes | Survives |
|---|---|---|---|---|
| Daily | SWD | Integrated probe ([sheet D2](sec_ai_d2)) | Flash + SRAM | — |
| 1 | SWD rescue debug port | Integrated probe | Chip reset | Hung firmware, code that reconfigures the debug pins, corrupt flash |
| 2 | Bootrom UART boot | Tier-3 pads, `SD2`/`SD3` | **SRAM only** | A missing or broken SWD probe. **Deprioritised** by [D59](sec_ai_q#d59) |
| 3 | Direct SPI to the flash die | Tier-3 pads + `RUN` low | Flash die | Everything short of physical damage. **A bring-up diagnostic**, not a recovery path |

- D1.13 — **Tier 0 is SWD and it is two signals plus ground.** Flash programming works by loading a flash algorithm into SRAM which then calls the bootrom's flash routines; OpenOCD handles that transparently, and **`picotool` is not available over SWD** — it speaks its protocol over USB only, so OpenOCD is the tool for this project.
  NOTE: **Tier 1 is the reason SWD is the primary path rather than merely the convenient one.** The debug architecture exposes a **rescue debug port** alongside the two cores, and it can reset the chip even when firmware is actively hostile to debugging — a tight loop, a routine that reconfigures the debug pins, a crashed sequencer. For an EC whose firmware sequences the rails that feed the FPGAs, that matters more than usual: **a bug in the sequencer must never leave the board unreachable.**
- D1.14 — **Tier 2 is the bootrom's UART boot, and its limitation is the whole reason [D1.15](sec_ai_d1#d115) exists.** The bootrom checks two straps at reset — `QSPI_SS` low enters BOOTSEL, `QSPI_SD1` high selects UART rather than USB — and then speaks 1 Mbaud on `QSPI_SD2` and `QSPI_SD3`. Those are flash-interface pins, not GPIO, and are not remappable; it is a different UART from the console the probe carries. **It writes only to SRAM. It cannot program flash.**
  NOTE: The strap is safe because the bootrom leaves chip select output-disabled and pulled high, so the in-package flash stays deselected, is never clocked, and its data pins stay high-impedance rather than opposing the `SD1` strap.
  NOTE: **The RAM flash-writer stub is what makes tier 2 useful, and it is a real deliverable that must exist before it is needed.** Built to link entirely into SRAM, it receives the payload over that same bootrom UART and writes flash by calling the bootrom's own flash functions, with a **CRC-32 readback** to verify — and the assembly CRC-32 from [Y2.4](sec_ai_y2#y24) is reusable for it unchanged. About 200 lines. **Archive the built binary alongside every EC firmware release: a recovery tool that has to be rebuilt from source during an emergency is not a recovery tool** (→ [Q107](sec_ai_q#q107)).
  NOTE: **It is off the critical path before E0.** Tier 1 now reaches a blank flash, a corrupt flash, an unpowered machine and a self-resetting one through the integrated probe, so tier 2 is left with the narrow case where SWD is physically broken and the bootrom still answers. The stub is still worth writing; it stopped being the thing that has to exist first ([D2.23](sec_ai_d2#d223), [D59](sec_ai_q#d59)).
- D1.15 — **Tier 3 addresses the flash die directly, and it works because holding `RUN` low puts the processor's QSPI pins in high impedance.** The in-package die is a standard part that speaks single-bit SPI, so four signals — chip select, clock, and the two data lines — are enough, and all of them are on the tier-3 pads. Any SPI flash programmer will do.
  NOTE: **The hazard is that those nets are simultaneously exposed and connected to the in-package flash die**, and it is why the header is gone: the six pads sit **immediately beside the package**, reached by pogo pin or clip, with **no cable and no connector** on them ([D2.22](sec_ai_d2#d222)). Route them away from the SDRAM, the backlight boost and the boost converter's switching node, and ground-guard them if there is room. Closes [Q108](sec_ai_q#q108).
  NOTE: **Its job changed with its footprint.** Tier 3 is no longer a recovery mechanism but the E0 assembly check — **JEDEC ID read with `RUN` low proves the rails, the QFN-80 joints and QSPI pad continuity at once**, with no probe firmware and no OpenOCD in the picture, which is exactly what is wanted when SWD refuses to attach and the question is whether the fault is in the solder or in the software ([D2.22](sec_ai_d2#d222)). **If layout cannot keep the stubs to a few millimetres, it is dropped rather than compromised.**

## The hub IC and its power.

- D1.16 — **The candidate is a four-port hub that runs standalone from pin strapping, with per-port power control and overcurrent sense**, chosen over two cheaper parts on documentation grounds: it is the only candidate whose datasheet meets the project's no-black-boxes rule, and per-port control lets the EC kill a misbehaving port without cycling the whole bus. **The cost delta is irrelevant against the schedule cost of debugging an undocumented part.** A cheaper SSOP part with gang-only power control remains defensible if hand-assembly ease dominates on the prototype board, since it is the easiest of the three to rework (→ [Q109](sec_ai_q#q109)).
  NOTE: Configuration rules that are easy to get wrong. **Strap it self-powered**, so it can declare 500 mA per downstream port — a bus-powered hub cannot. Follow the crystal's load capacitance exactly; **crystal error is a common cause of intermittent enumeration.** Strap unused downstream ports off rather than leaving them floating. **Do not populate the configuration EEPROM** — pin strapping is sufficient and removes a failure mode. And **do not release the hub from reset with an RC**: it must be powered and out of reset *before* the EC begins enumerating, so the ordering belongs in EC firmware where it is explicit.
- D1.17 — **Per-port current-limit switches driven by the hub's port-power outputs, with the fault line returned to the hub**, and 120 µF of bulk capacitance downstream of each switch to absorb hot-plug transients. **Do not omit the per-port limiting: a short on a user-accessible connector must not take down the system.**
  NOTE: **The current budget does not close on a portable, and that is a policy question rather than a component one.** Typical draw is the hub's 30 mA plus a keyboard and a mouse at 50 mA each — 130 mA, 0.65 W. Worst case is three ports at 500 mA plus the hub: **1.55 A, 7.75 W**, which a 1S battery is not going to deliver. Two answers: a single aggregate current limit ahead of the hub, letting the per-port switches handle faults only; or **the EC reading each device's declared maximum during enumeration, keeping a running total, and refusing to configure a device that would exceed the budget, saying so on the console**. The second is preferable — it is the honest behaviour, it is visible to the user, and it is exactly the kind of policy an EC should own (→ [Q110](sec_ai_q#q110)).
  NOTE: `VBUS_EN` for the whole USB subsystem becomes another switched rail in the REV C sequence: **the hub and every port stay dead until the system is up** ([C.19](sec_ai_c#c19)). Verify the boost converter's output capability at the chosen aggregate limit with the battery low, at 3.4 V in, before the schematic is frozen (→ [Q111](sec_ai_q#q111)).
- D1.18 — **Signal integrity, four pairs of it**: 27 Ω series resistors on the EC's `D+`/`D−` close to the pin, 90 Ω differential routing matched in length on the upstream pair and all three downstream ones, and **ESD protection on every downstream pair and its VBUS** — these are user-accessible connectors. The host-mode pull-downs are internal to the part and need no external components.

## Boot, the flash it boots from, and the way firmware gets replaced.

- D1.21 — **The EC's in-package flash is the system's configuration store, and it cost nothing to make it one.** Three iCE40 HX8K bitstreams are ~135 KB each — **~405 KB** — against 2 MB in the package, and `bios.bin` fits beside them with room for two complete copies of everything ([D1.24](sec_ai_d1#d124)). **This is the decision the rest of this sheet's boot story follows from** ([D60](sec_ai_q#d60)).
  NOTE: **Bitstream size is fixed by the device, not by the design.** iCE40 configuration SRAM is a constant, so a trivial gateware image and a full one produce almost identically sized bitstreams — utilisation does not enter into it. Compression helps, and helps most on the sparse designs that need it least. **Budget against the uncompressed figure**, and measure it from a real `icepack` run rather than from this estimate before the layout below is frozen (→ [Q127](sec_ai_q#q127)).
  NOTE: What it deletes is worth more than what it costs: **the '3257 mux and its six EC pins, the SD ownership handoff with its atomicity requirement and its state machine, the SD driver and filesystem in EC firmware, and the card itself from the critical boot path** ([G.1](sec_ai_g#g1), [G.2](sec_ai_g#g2)). The EC gains a flash layout to manage, which is a table.
  NOTE: **The alternatives were examined and both were rejected on their own terms.** **NVCM** is one-time-programmable — closer to fuses than to flash — so a device programmed with it carries that bitstream permanently, which is unusable for a design that will iterate, and open-toolchain support for it is uncertain besides. **A dedicated SPI flash per FPGA** in master mode adds three parts and their routing to solve a problem the EC's flash already solves at zero BOM cost; **one shared flash in master mode across three devices** additionally leans on the `CBSEL` cold-boot multi-image feature — a less-travelled path — and still needs the same staggered `CRESET_B` release as the EC-mastered scheme, so it removes no complexity in exchange (→ [D62](sec_ai_q#d62)).

| Region | Size |
|---|---|
| Bootloader / slot selector | 32 KB |
| **Slot A** — EC firmware + 3 bitstreams + `bios.bin` | ~600 KB |
| **Slot B** — the same | ~600 KB |
| Configuration storage | 64 KB |
| Spare | ~700 KB |

  NOTE: Provisional pending measurement of both the bitstreams and `bios.bin` (→ [Q127](sec_ai_q#q127)).

- D1.22 — **The boot state machine.** Nine states, `S_FAIL` reachable from any configuration step, and no external medium in any of them.

| State | Action | Exit |
|---|---|---|
| `S0_POR` | EC boots from in-package flash; the bootrom selects the active slot. Every rail but 3V3_AON off, `CRESET_B` asserted on all three FPGAs, `RESB` asserted | EC firmware running |
| `S1_POWER` | Rails in REV C order — 1V2, then 3V3_MAIN — respecting the iCE40's VCC-before-VCCIO/VPP requirement ([C.8](sec_ai_c#c8)), each waited on by its `PG` | Rails stable |
| `S2_CFG_NEON` | Configure **Neon** from EC flash over SPI slave. **From `CDONE_B` onward every state below is reportable on the panel** ([D1.23](sec_ai_d1#d123)) | `CDONE_B`, or → `S_FAIL` |
| `S3_CFG_HELIUM` | Configure **Helium** | `CDONE_A`, or → `S_FAIL` |
| `S4_CFG_C` | Configure FPGA-C if populated; **skip on timeout** | `CDONE_C`, or skipped |
| `S5_BIOS` | Transfer `bios.bin` from EC flash into the pinned SRAM zone by `MEM_WRITE` over the mailbox; verify | Transfer verified |
| `S6_RELEASE` | Release `RESB` | CPU running |
| `S7_RUNTIME` | Service HID, console, power management, update requests | — |
| `S_FAIL` | Report on the panel where there is one, on the UART and the status LED where there is not; halt | Reset only |

  NOTE: **`S4` skipping on timeout is what makes FPGA-C optional in hardware rather than in intention.** Configuration is per-device by chip select rather than a chain, so an unpopulated FPGA-C is simply a `CDONE_C` never observed — **no jumper, no footprint provision, no effect on the other two** ([D3.7](sec_ai_d3#d37)).
  NOTE: **Boot time is comfortably inside what was accepted.** Three 135 KB bitstreams at 25 MHz is ~50 ms of clocking plus per-device setup, so the whole of `S0`–`S6` lands in the low hundreds of milliseconds. Seconds were tolerable; this is not close to the limit.
- D1.23 — **The panel is the boot console from `S2` onward, and the ordering exists to make that true.** Only `S1` and `S2` can fail with no display — everything after them, Helium's configuration and the BIOS transfer included, reports in text on the machine's own screen ([D1.2](sec_ai_d1#d12), [T.64](sec_ai_t#t64)). Below `S2` there is the debug UART and a distinguishable LED blink pattern, and that is the whole of it.
  NOTE: **A missing microSD is no longer anywhere in this list.** The card is Helium's and is discovered by the running system ([G.2](sec_ai_g#g2)), so an empty slot produces a message from a booted machine rather than a halt in `S_FAIL`. That is the concrete thing [D60](sec_ai_q#d60) bought a user.
- D1.24 — **Field update: two complete slots, written inactive-then-switch, and EC firmware is inside the scheme rather than beside it.** `FLASH_BEGIN` declares the target slot and total length, `FLASH_DATA` carries the payload, `FLASH_COMMIT` verifies a CRC and activates the slot — all of it **Helium → EC**, the one bulk flow that runs in that direction ([D3.12](sec_ai_d3#d312)). The image arrives on the microSD, and the 65816 pushes it.
  NOTE: **An earlier revision excluded the EC's own firmware on the grounds that a failed update meant opening the chassis. The integrated probe removed that objection** ([D2.2](sec_ai_d2#d22)): a bricked EC is recovered through the chassis debug port with SWD against blank flash, on a machine that need not even be powered ([D1.13](sec_ai_d1#d113)). **The three conditions that recovery rests on are all load-bearing and all stated as prohibitions** — the OTP debug-disable bits are never burned ([D1.19](sec_ai_d1#d119)), the probe is powered from debug-port VBUS with backfeed protection ([D58](sec_ai_q#d58)), and the probe's own `BOOTSEL` is reachable on a pinhole ([D2.5](sec_ai_d2#d25)).
  NOTE: **Throughput is poor and that is acceptable.** Hundreds of KB through the mailbox with a 65816 at 8 MHz emitting the commands takes minutes. It is a firmware update; it is allowed to take minutes.
  NOTE: **The whole feature is optional.** The primary programming path throughout development is USB → probe → SWD ([D1.13](sec_ai_d1#d113)), and self-update is an exercise in making the machine self-sustaining rather than a requirement. **The bootrom's own partition-table A/B support with version numbering may make the slot selector something that need not be written by hand at all** — which must be verified against the vendor documentation before anything is built on it (→ [Q128](sec_ai_q#q128)).
- D1.25 — **While it erases a sector the EC is deaf, and this must be a designed state rather than a discovered one.** The core executes from flash over XIP and cannot run flash-resident code while erasing: the writer is marked `__not_in_flash_func()`, interrupts are disabled — handlers are flash-resident too — and core 1 is parked with `multicore_lockout`. **For the 30–50 ms a 4 KB erase takes there is no HID service, no mailbox polling, and no response of any kind.**
  NOTE: **The reason it needs designing is that its symptom is indistinguishable from a fault.** The EC holds the 10-second watchdog and the shutdown state machine ([D1.7](sec_ai_d1#d17)), so an EC that stops answering is exactly what a hung EC looks like — and a user pressing keys during an update will see them dropped. The running system has to *know* input will stall, and say so, rather than the stall being something the machine recovers from silently (→ [Q129](sec_ai_q#q129)).
  NOTE: Granularity and endurance are not the constraint: 4 KB erase, 256 B program, ~100k erase cycles per sector, which at update frequencies is irrelevant.
- D1.26 — **All debug access to this machine passes through EC firmware, and if that firmware hangs it is lost all at once** — Helium, system memory and the console together. SWD reaches the EC's own Cortex-M33, not Helium; reaching the Debug Agent by that route still needs EC firmware running to bridge it ([D1.3](sec_ai_d1#d13), [sheet R](sec_ai_r)).
  NOTE: **Accepted, on the grounds that it matches essentially any modern laptop**, and mitigated by discipline rather than by architecture: the EC's command bridge stays simple, non-blocking and watchdogged, and the per-transaction watchdog on the Debug Agent side ([R.17](sec_ai_r#r17)) stays specified.
  NOTE: **A hung EC and a bricked EC are different, and both are recoverable.** Hung loses debug access to the *system* while the EC itself is still reachable over SWD; bricked is [D1.24](sec_ai_d1#d124)'s case and is reachable against blank flash. **The unrecoverable case needs a blank flash *and* burned OTP debug-disable bits at the same time**, which is precisely why [D1.19](sec_ai_d1#d119) is a prohibition rather than a preference.

## Do not do — the list of irreversible or expensive mistakes, kept together deliberately.

- D1.19 — **Do not program the OTP.** Secure boot and the bootrom-UART disable are irreversible, and programming the security bits **disables SWD permanently and removes tiers 1 and 2 at the same stroke**. The EC has no threat model that requires them.
- D1.20 — **Do not route the tier-3 pad stubs near the SDRAM, the backlight boost or the boost converter's switching node, and do not put a connector on them** ([D1.15](sec_ai_d1#d115), [D2.22](sec_ai_d2#d222)) · **do not release the hub from reset with an RC** ([D1.16](sec_ai_d1#d116)) · **do not omit per-port current limiting** ([D1.17](sec_ai_d1#d117)) · **do not populate the hub's configuration EEPROM**.

## Gate plan · U0–U8 — the USB and programming path, brought up separately from everything else.

- [ ] U0 — **Hub IC selected, power policy decided, tier-3 pads placed or abandoned.** [Q109](sec_ai_q#q109), [Q110](sec_ai_q#q110) and [Q106](sec_ai_q#q106) closed; the pad placement judged against [D2.22](sec_ai_d2#d222)'s abandonment condition.
- [ ] U1 — **Schematic captured**, with every USB and debug net reviewed against this sheet.
- [ ] U2 — **Board powered and the EC programmed over SWD.** OpenOCD programs and verifies; console output over the integrated port. Depends on [V3](sec_ai_d2#v3) and [V4](sec_ai_d2#v4) of [sheet D2](sec_ai_d2), which bring the probe up first.
- [?] U3 — **The RAM flash-writer stub validated** — firmware written to flash over the bootrom UART on the tier-3 pads and verified by CRC-32 readback. **No longer gates the others** ([D2.23](sec_ai_d2#d223)).
- [ ] U4 — **The host stack enumerates with `JP-BYPASS` in bypass.** A Full Speed device enumerates directly and reports on the console.
- [ ] U5 — **The host stack enumerates through the hub.** Hub descriptor read, port power applied, a device on port 1 enumerated.
- [ ] U6 — **A Low Speed device behind the hub.** A keyboard reports HID data. Closes [Q102](sec_ai_q#q102).
- [ ] U7 — **Cascade behaviour characterised.** An external hub either works or is refused gracefully. Closes [Q103](sec_ai_q#q103).
- [ ] U8 — **The power policy enforced.** A device exceeding the budget is refused at configuration and the refusal appears on the console.
