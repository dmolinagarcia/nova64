# WebAssembly and the browser
> a library with no main · what the browser supplies · and what a headless test cannot see

The emulator compiles to WebAssembly and runs client-side, so nothing executes on the server and a plain static host is enough. That makes the machine reachable from anywhere without a toolchain, which matters more than it sounds: the development machine needs `cc65` to build a boot image and nothing else, while the module itself is built once wherever a modern clang lives. **The browser also supplies three things the native build could not**, and one of them is a requirement of [EM3.13](sec_ai_em3#em313) rather than a convenience.

## The module is a library, not a program, and every flag below was learned the hard way.

- EM5.1 — **It has no `main` and no entry point, so it is linked with no startup files and no entry.** Linking the C runtime startup object was wrong from the beginning: that object exists to call `main`, which this module does not have. **Dropping it took the module from 346 KB to 97 KB**, because the argument and environment machinery went with it, and it removed the one object that older linkers reject when the sysroot is newer than they are.
- EM5.2 — **The initialiser is exported by name rather than selected with the reactor execution model**, and the reason is a misdirecting error message. The reactor option is a WebAssembly-*target* option, so a clang built without that target reports it as an unknown **argument** — which reads like a version problem and is not one. The flags used instead are accepted by every clang, and the JavaScript host calls whichever initialiser the module exports, so an Emscripten build works too.
- EM5.3 — **Wasm support is probed by compiling a trivial file for `wasm32`, not by asking the compiler what targets it has.** The query option exists only from clang 13, so it fails on exactly the compilers worth catching. The build names your compiler when the probe fails, because the failure it is guarding against is a clang that reports a missing target as a bad flag.
- EM5.4 — **The WASI sysroot release must sit near your LLVM.** The linker reads the sysroot's objects and the wasm object format has changed over the years, so a much older linker refuses a much newer sysroot. Release 11 was built with LLVM 10, 12 with 11, and so upward; the emulator uses only stdio, stdlib, string and math, so a libc of any vintage covers it — builds against release 11 and 25 behave identically.
  NOTE: The compiler-rt builtins are the awkward part. They come from the same release as a separate archive and **must go in the compiler's own resource directory**, because clang looks for them there and nowhere else.
- EM5.5 — **The module asks for 128 MB of initial memory**, because the backing arrays are about 70 MB ([EM4.6](sec_ai_em4#em46)).

## The host owns the clock, and nothing blocks the tab.

- EM5.6 — **The run loop is sliceable, and it has to be.** A blocking loop inside the module freezes the page, so the JavaScript host calls the module once per animation frame with a budget of one sixtieth of the nominal clock, then renders and paints to a canvas. **The module exports its statistics by index** rather than by struct offset, so the host needs no knowledge of the C layout and the two can be rebuilt independently.
- EM5.7 — **The JavaScript side answers WASI calls through a proxy** rather than a maintained list of stubs, so whichever calls a given build path pulls in are satisfied without the list going stale. Only the write call does anything.
- EM5.8 — **The built module is committed, and the drift hazard is guarded rather than accepted.** It changes only when the emulator's C changes, which is rare next to how often a boot image changes, so committing it lets a machine with no wasm toolchain serve and run the console. The hazard with any committed build output is that it drifts from its source and someone spends an hour debugging a change that was never compiled in — so a check compares the module against the sources and refuses to serve a stale one.

## What the browser supplies that the native build could not.

- EM5.9 — **A live pixel window**, which replaces the sequence of dumped image files the native build produces. This is the one host output that could not be provided any other way without taking on a host graphics library, and it is why interactive work happens in the browser ([EM4.14](sec_ai_em4#em414)).
- EM5.10 — **Pointer lock, which is exactly the capture mechanism [EM3.13](sec_ai_em3#em313) requires.** That sheet argues capture is functional rather than cosmetic under a relative-motion protocol, because an uncaptured host pointer stops producing deltas at a screen edge. Pointer lock is that mechanism and the movement deltas it reports are precisely the stream the mailbox carries — so the requirement is met by a browser API rather than by anything the emulator had to build.
- EM5.11 — **Physical key identity, for free.** The browser's key *code* names a key by position rather than by the character it produces, so a Spanish, US or Dvorak host keyboard all deliver the same scancode. [EM3.9](sec_ai_em3#em39) requires that host layout must not leak into the guest; the code property gives it and the key property would not. **Choosing the wrong one of those two is a one-word bug that would survive to hardware.**

## Serving it.

- EM5.12 — **Any static host, with one header requirement and one that does not apply.** The module must be served as `application/wasm` for streaming instantiation to work, which Python's own server does correctly from 3.11. **No cross-origin isolation headers are needed**, because the emulator is single-threaded and uses no shared array buffers — worth stating, since those headers are the usual first thing reached for and they would constrain hosting for no reason here.

## Measured, and neither hot spot is the CPU core.

- EM5.13 — **23.2 Mcycle/s under node after JIT warm-up**, on the text-mode workload: **2.9× real time at 8 MHz**, and **0.5× at 50 MHz**. Comfortable for the current target with headroom to spare; a 50 MHz softcore ([sheet E](sec_ai_e)) would not run in real time without optimisation work.
  NOTE: The first measurement said 2.6 Mcycle/s and was wrong by nine times, because it timed the JIT warm-up and a 70 MB allocation inside the loop. **If a benchmark surprises you, suspect the harness before the code.**
- EM5.14 — **Two things dominate the profile and both are rendering.** The text renderer repaints all 9600 character cells whenever the framebuffer is read, which is 614,400 pixel writes per frame; and the frame converter turns the whole framebuffer into RGBA every frame. **Both need dirty-region tracking before anything interactive**, and neither is on the critical path for correctness ([EM6.18](sec_ai_em6#em618)).
- EM5.15 — **Native and wasm agree to the bit, and that is worth more than either passing its own tests.** The same boot image produces identical cycle counts, identical text output and identical framebuffer content under both builds. Two independent builds of one source agreeing exactly is a stronger statement than either looking correct alone, and the port earned its keep once already by forcing the abort model of [EM4.2](sec_ai_em4#em42).

## What the headless test covers, and what it cannot.

- EM5.16 — **The browser shell is tested under jsdom with stubs, driving the real flow** — load an image, press run, run frames, capture input, type, move the mouse — with 22 checks passing. The assertions read the machine's own counters rather than checking that nothing threw: the tee delivers characters matching the native build exactly, the canvas receives a frame whose lit pixel count matches the native render exactly, a mapped key delivers two mailbox events, an unmapped key delivers none, and pointer motion is delivered while captured and dropped once capture is released.
- EM5.17 — [[open]] **The stubs are precisely the parts most likely to be wrong, so the wiring is verified and the presentation is not.** The 2D canvas is recorded rather than rendered, so nothing here proves the frame looks right, that pixelated scaling behaves, or that a 1024-wide canvas scaled down by CSS stays legible at 8-pixel glyphs — **that last is the most likely thing to be wrong**. Pointer lock is synchronous in the harness and asynchronous in reality, with browsers differing on movement scaling and acceleration. Key events are synthesised without modifiers, repeat or input-method involvement, and some codes will be swallowed by the browser before the page sees them. CSS is parsed and not applied. And streaming instantiation is fed a synthetic response, so the content type of [EM5.12](sec_ai_em5#em512) is untested by construction.
  NOTE: Believing headless coverage is browser coverage is the trap the whole item exists to name. What remains is a short list of things a person has to look at once, on a real display, with a real mouse.
