# Filesystems — the VFS layer
> one syscall path · the vnode model · who owns what

The machine is about to have two filesystems — NVFS on the system volume ([sheet Y2](sec_ai_y2)) and ext2 on whatever card arrived from a host ([sheet Y3](sec_ai_y3)) — and one syscall table that has to reach both. This sheet is the layer that stops that from becoming two access paths and a branch on filesystem type at every call site. It is specified **before** the ext2 driver exists, and that ordering is the whole economy of it: introducing it now costs one module and a mechanical rework of NVFS's call surface; introducing it afterwards costs the same rework applied to two drivers, plus a syscall layer that has already grown the branches. It supersedes the one-line sketch at [J.6](sec_ai_j#j6).

- Y1.1 — **The layer exists for a second reason, and it is the one that survives the first.** Some decisions cannot live inside a filesystem driver at all: mount-point traversal, symlink loop bounds, vnode identity, cross-mount rejection, and the locking discipline the Amiga milestone will need. Neither NVFS nor ext2 can see across a mount boundary, and neither can know that another volume has been grafted onto one of its own directories. **Those decisions have no correct home except here**, and that is true even in the counterfactual where the machine only ever has one filesystem.
- Y1.2 — **It is not a Unix VFS, and the difference is a rule rather than a preference.** Every operation in the tables below is one that *both* drivers implement without emulation. Nothing is added because Unix has it. The interface is cheap to extend and expensive to shrink, which is the asymmetry that decides where the default sits.
- Y1.3 — **What is actually being unified is narrower than the two formats are**, and the divergences below are what the interface may not expose. Block size differs — 2048 in NVFS because it equals the MMU page ([L.1](sec_ai_l#l1)), 1024 in ext2's write path — so **block size is a mount property and never a constant**. File layout differs — extents against a triple-indirect tree — so `read` and `write` take byte offsets and nothing else. Directory position differs — a slot index against a byte offset — so the `readdir` cookie is an opaque `uint32_t` the VFS stores and hands back without interpreting. Metadata consistency differs — a redo journal against ordered writes — so writeback ordering stays under driver control ([Y1.14](sec_ai_y1#y114)).
  NOTE: **One row of that comparison came out better than it had to.** NVFS draft 3 adopted POSIX-identical `mode` and type encodings ([Y2.9](sec_ai_y2#y29)), so `vattr.mode` passes through both drivers unchanged and there is **no translation table in either direction** — not in `getattr`, not in `readdir`, not in `create`. Had the two formats disagreed on a single nibble, every one of those would carry a conversion, twice.
- Y1.4 — **Four objects, with ownership stated rather than implied.** `mount_t`, one per mounted volume, holding `vfs_ops` and the driver's private state — VFS-owned. `vnode_t`, one per *in-use file*, cached and refcounted, identity `(mount, file_id)` — VFS-owned. `file_t`, one per `open()`, holding an offset and flags — VFS-owned. And the descriptor table, index → `file_t*` — owned by the process.
- Y1.5 — **`file_t` is separate from `vnode_t` because two `open()` calls need independent offsets and a `dup()` needs a shared one.** Only the three-level structure gives both. It costs about ten bytes per open file to have from the start and an audit of every call site that assumed the offset lived in the vnode to add later.
- Y1.6 — **The vnode cache is the VFS's and not each driver's**, and the argument is a corruption rather than a tidiness one: if two open files on the same underlying file hold two copies of the inode, an append through one silently discards the size and the block pointers written by the other. Both drivers need an in-memory identity map for exactly this reason — **it is the same logic, it needs the same LRU pressure, and mount traversal has to inspect it**, so writing it twice is writing the same 300 lines twice and then keeping them in step.
- Y1.7 — **`lookup` returns a `file_id`, never a vnode.** This is the single load-bearing line of the interface. A driver cannot know whether a vnode is already cached and cannot know whether a mount is grafted onto the result; the VFS takes the identifier, consults its cache, and calls `vget` only on a miss. Getting it backwards leaks the vnode cache into both drivers and cannot be unpicked later.
  NOTE: Which puts a hard requirement on [sheet Y2](sec_ai_y2): **NVFS must expose a stable 32-bit file identifier that does not change when the file is modified**, because the cache is keyed on it. Its inode number satisfies this, and `i_generation` ([Y2.8](sec_ai_y2#y28)) makes the pair unique over the life of the volume (→ [Q90](sec_ai_q#q90)).
- Y1.8 — **Directory-mutating operations take a parent vnode plus a name, never a path.** Resolution happens once, here. **A driver never sees a `/`.**
- Y1.9 — **Write operations may be `NULL`, and the VFS answers `E_NOTSUP`.** That is not defensive coding; it is what makes a read-only ext2 mount a genuinely smaller deliverable rather than a full driver with stubs in it ([Y3.16](sec_ai_y3#y316)).
- Y1.10 — **There is no `open` or `close` in the per-vnode table.** Opening is a VFS act — resolve, check the type, allocate a `file_t` — and neither driver has per-open state. A device filesystem would need them; adding two slots at that point is trivial, and the shape of that question is [Q95](sec_ai_q#q95).

## Operation tables — split per mount and per vnode, which is the natural division of the operations rather than a convention borrowed.

| Table | Operations |
|---|---|
| `vfs_ops`, per mount | `mount` · `unmount` · `root` · `sync` · `statfs` · `vget` (VFS wants a vnode it has not cached) · `vput` (last release; the driver frees its private state and, if the link count is zero, performs the deferred delete) |
| `vnode_ops`, read half | `lookup` · `read` · `readdir` · `getattr` · `readlink` |
| `vnode_ops`, write half — `NULL` on a read-only driver | `write` · `truncate` · `setattr` · `create` · `mkdir` · `rmdir` · `unlink` · `link` · `symlink` · `rename` · `fsync` |

- Y1.11 — **Path resolution is the VFS's, and drivers supply `lookup` on one component.** Absolute paths start at the root mount's root vnode, relative ones at the process's cwd; empty components and `.` are skipped. `..` at the root of a mount **steps out to the covering vnode first** and then resolves `..` there; at the root of the root mount, `..` is the root. A vnode carrying `VF_MOUNTED` is descended into. **Symlinks are followed here and are bounded at 8 traversals per call**, beyond which the answer is `E_LOOP`.
  NOTE: The two steps that could not be delegated are the mount ones, and a third is nearly as bad: a symlink stored on ext2 may name a path that resolves on NVFS. `readlink` is per-driver, because the two store short targets differently — ext2 packs a target under 60 bytes into `i_block[]`, NVFS stores one under 72 bytes inline in the inode ([Y2.11](sec_ai_y2#y211)) — but *following* is not.
  NOTE: `nameiparent` exists beside `namei` because every mutating call needs the containing directory plus the final component, and resolving the whole path first fails on `create` by construction.
- Y1.12 — **Resolution is iterative, not recursive per component**, and the reason is [L.11](sec_ai_l#l11) rather than taste: VFS operations run in process context on a per-process kernel stack, every one of which lives in bank `$00` and is addressed by a 16-bit `S`. That is the scarcest address space in the machine. **The budget is 512 bytes of kernel stack for any VFS operation**, the symlink bound of [Y1.11](sec_ai_y1#y111) bounds its share, and ext2's indirect walkers — read *and* truncate — recurse at most three deep and no deeper ([Y3.5](sec_ai_y3#y35)).
  NOTE: The corollary is a rule that is easy to break by accident and produces an overflow into the neighbouring process's kernel stack, which is close to undebuggable: **the 262-byte directory-entry structure is always caller-provided and is never a stack local inside the VFS.** The syscall layer keeps one per open directory descriptor, not one per process.
- Y1.13 — **Four mount slots**: the root (NVFS), one removable ext2, two spare. The root mount is established at boot and cannot be unmounted. `mount` requires the mountpoint to resolve to a directory, sets `VF_MOUNTED` and pins that vnode for the volume's lifetime; `unmount` fails with `E_BUSY` if any vnode of that mount other than its root is still referenced — **which is what stops a card being pulled while a file on it is open**, and costs one scan of the vnode cache.
  NOTE: A requested read-write mount **may be downgraded by the driver**, which ext2 does whenever the feature policy of [Y3.4](sec_ai_y3#y34) demands it. The VFS records the result and reports it through `statfs`, and the caller is told: a silent downgrade to read-only produces confusing failures much later and in a different part of the system.
- Y1.14 — **One block cache below the VFS, not one per driver — and the ordering hook is the part worth arguing about.** Two independent caches means two pools sized by guesswork, no global LRU, and one mount's buffers sitting idle while the other thrashes. The shared cache holds **uniform 2048-byte buffers**, of which an ext2 mount uses half; that wastes 50 % while an ext2 mount is active, and it is accepted because ext2 is a transfer medium and NVFS is the resident root, while a two-size slab allocator costs more code than the memory it saves at this scale.
  NOTE: **The complication is that NVFS's journal forbids a naive global LRU.** A dirty metadata block must not reach the card before its journal record has committed ([Y2.15](sec_ai_y2#y215)), and an eviction at an arbitrary moment breaks exactly that. The mechanism is **a `commit_seq` per buffer and a `flushed_seq` per mount**: the cache refuses to write back a buffer whose sequence exceeds its mount's, and calls `ops->sync` to advance it first. ext2 leaves the field at zero and is unaffected. Four bytes per buffer and one comparison in the eviction path.
  NOTE: It is still a hook whose semantics one driver uses, which is a smell, and the honest form of the trade is that **the hook's cost is one field and the alternative's cost is permanent** (→ [Q91](sec_ai_q#q91)). Explicit `bpin`/`bunpin` exists beside it, used by both drivers for superblocks and descriptor tables.
  NOTE: What is **not** proposed: a page cache, read-ahead beyond the multi-block transfers [G.7](sec_ai_g#g7) already provides, and any unification with the SRAM. **The SRAM is a hardware-managed cache over SDRAM and must not be statically carved up for filesystem buffers** ([F.5](sec_ai_f#f5)); all of this lives in SDRAM.
- Y1.15 — **One error space, because these values reach userland through the `COP` ABI** ([J.3](sec_ai_j#j3)). Each driver keeps its internal enumeration — the detail is useful inside the driver and meaningless to a caller — and maps at its `vnode_ops` boundary.
  NOTE: **`E_XDEV` is checked here and cannot be checked anywhere else.** `link` and `rename` compare the two directories' mounts before dispatching; a driver handed a vnode belonging to a different mount dereferences the wrong private pointer, which is not an error it can detect.
  NOTE: **`E_CORRUPT` is sticky.** When a driver reports it the VFS marks the mount read-only and latches the condition. Continuing to write to a filesystem that has already failed a consistency check is how a recoverable problem becomes an unrecoverable one — [Y3.10](sec_ai_y3#y310) states it for ext2, and it belongs here so that it holds for both.

## Unified error space — the values a process sees.

| Code | Meaning | Code | Meaning |
|---|---|---|---|
| `E_OK` 0 | success | `E_BUSY` −11 | mount or vnode in use |
| `E_IO` −1 | device failure | `E_LOOP` −12 | symlink bound exceeded |
| `E_NOENT` −2 | no such name | `E_NAMETOOLONG` −13 | |
| `E_EXIST` −3 | | `E_MFILE` −14 | descriptor table full |
| `E_NOTDIR` −4 | | `E_BADF` −15 | |
| `E_ISDIR` −5 | | `E_XDEV` −16 | cross-mount link or rename |
| `E_NOTEMPTY` −6 | | `E_CORRUPT` −17 | structural inconsistency — sticky |
| `E_INVAL` −7 | | `E_FEATURE` −18 | unsupported on-disk feature |
| `E_NOSPC` −8 | no blocks | `E_NOTSUP` −19 | operation `NULL` in this driver |
| `E_NOFILE` −9 | no inodes | `E_FBIG` −20 | |
| `E_ROFS` −10 | | `E_NOTMOUNTED` −21 | |

- Y1.16 — **Permissions are read, preserved and reported — and never enforced.** The machine has no user model, so there is nothing to enforce them against, and enforcing them with a single implicit root user produces obstacles and nothing else. Files created here take `uid = gid = 0`, mode `0644` for regular files and `0755` for directories. Revisit only if the machine ever grows multiple users, which is on no roadmap.
- Y1.17 — **The VFS supplies the timestamp; a driver never calls the clock.** `vfs_now()` is one function, and with no RTC on the board it returns zero ([Y2.4](sec_ai_y2#y24)). When an RTC arrives, one function changes — and **the absence of one is a hardware gap rather than a filesystem question**, which is why it is [Q88](sec_ai_q#q88) rather than an item on this sheet. `atime` is never updated on read in either driver, because doing so turns every read into a write.
- Y1.18 — **Deferred delete, and it costs nothing to have from the start.** `unlink` on a file with open descriptors decrements the link count and returns; the blocks are released in `vput`, when the last vnode reference goes and the link count is zero. Both drivers implement it in their `vput`, and the VFS guarantees the ordering by holding the vnode reference for as long as any `file_t` points at it. **This is what makes deleting an open file safe rather than catastrophic.**
- Y1.19 — **The locking discipline is written now and the primitives are no-ops until the Amiga milestone.** The Apple II milestone is single-threaded — one program, one call into the filesystem at a time — and every shared structure here becomes a race the moment [sheet N](sec_ai_n)'s scheduler preempts. Retrofitting locking into a vnode cache is notoriously painful and fails intermittently rather than cleanly, whereas specifying it now costs a handful of macros that compile to nothing.
  NOTE: **The rule that is expensive to discover late is the ordering one, so it is stated first: parent before child, and between siblings, lower `file_id` first.** That is what makes cross-directory `rename`, which holds two directory locks, deadlock-free — and the deadlock it prevents appears only under concurrent renames in a running GUI. The rest: a vnode is locked across any operation that reads or writes its metadata; a vnode lock is never held across a block-device wait that is not part of the operation; and the reference count and the lock are independent — **holding a reference does not imply holding the lock.**
  NOTE: Once processes are preemptive, an SD read of several milliseconds must not spin: the caller sleeps and the scheduler runs somebody else ([N.3](sec_ai_n#n3)). That is what puts VFS operations in process context and makes [Y1.12](sec_ai_y1#y112)'s stack budget binding rather than advisory.
- Y1.20 — **The syscall table does not change; what sits behind the dispatch does.** `open` is `namei` — or `nameiparent` plus `create` for `O_CREAT` — then a `file_t` installed in the descriptor table. `read`/`write` are the driver's, at the file's offset, which is then advanced; `pread`/`pwrite` are the same without the advance. `lseek`, `chdir`, `dup` and `dup2` never reach a driver at all. `opendir`/`readdir` are a `file_t` with the directory flag and the cookie kept in its offset field.
  NOTE: **`getcwd` deserves its own decision and gets the cheap answer.** Reconstructing a path from a vnode means walking `..` upward and scanning each parent for the entry whose identifier matches the child — O(depth × entries), with no cache, and it simply cannot resolve an unlinked working directory. **The current directory is stored as a string in the process control block** beside the vnode reference, updated on `chdir`, which costs 64–128 bytes per process and makes `getcwd` a copy ([N.1](sec_ai_n#n1)).
- Y1.21 — **The host-side F-series of [sheet P](sec_ai_p#p26) is where this interface is discovered rather than designed**, and it has one shape requirement attached. libfuse offers a path-based high-level API and an inode-based low-level one; **only the low-level shape transfers**, because path resolution, symlink following and mount crossing are all VFS responsibilities here and a driver never sees a path. The vtable that track builds must therefore key on inode number with `lookup(parent, name)`, and then a driver here is a thin adapter over the same functions rather than a parallel implementation (→ [Q92](sec_ai_q#q92)).
  NOTE: Two further shapes must not leak back: FUSE supplies uid and gid and expects permission checks, which [Y1.16](sec_ai_y1#y116) does not have; and libfuse is multi-threaded unless told otherwise, which would make its threading model a dependency of this one. **Run the host implementations single-threaded.**

## Budgets — against roughly 19 KB for ext2 read-write and 9 KB read-only ([Y3.13](sec_ai_y3#y313)), plus NVFS.

| Code | Estimate | RAM | Size |
|---|---|---|---|
| Vnode cache and lifecycle | 1.5 KB | Vnode cache, 24 × 28 B | 672 B |
| Path resolution, symlinks, mount crossing | 1.5 KB | Mount table, 4 × 48 B | 192 B |
| Mount table | 0.5 KB | Open file objects, 24 × 10 B | 240 B |
| `file_t`, descriptor table, syscall glue | 1.5 KB | Descriptor table, 16 × 3 B | 48 B per process |
| Error mapping, `statfs`, miscellany | 0.5 KB | cwd string | 128 B per process |
| **Total** | **≈ 5.5 KB** | Path scratch | 320 B |
| | | **Total, excluding per-process** | **≈ 1.4 KB** |

  NOTE: Small against the block cache's ~20 KB ([Y3.14](sec_ai_y3#y314)). The vnode cache size of 24 is a guess and should exceed the maximum number of simultaneously open files by a margin, since directory vnodes along active paths are held too (→ [Q94](sec_ai_q#q94)).
  NOTE: **If the whole filesystem stack has to be resident, address space is the constraint rather than code size**, and it should be checked against the kernel's bank `$01` budget before the ext2 driver is started rather than after ([J.1](sec_ai_j#j1)).

## Phasing · V0–V5 — V6 is the Amiga milestone and needs no work before it.

- [ ] V0 — **Structures, error space and the header frozen.** `vfs.h` compiles under both host GCC and Calypsi, and the static assertions pass on both.
  NOTE: The identifier question of [Y1.7](sec_ai_y1#y17) is answered before this gate, not during it.
- [ ] V1 — **Vnode cache, mount table and `namei`.** A stub in-memory filesystem mounts at `/` and resolves paths, on the host.
- [ ] V2 — **NVFS reworked behind `vnode_ops`.** Its existing test suite passes unchanged through the VFS.
  NOTE: **This is the gate that must happen before the ext2 driver is started, and it is the one with the least visible payoff** — a rework of code that already works. Which is precisely why it is easy to skip and expensive to have skipped.
- [ ] V3 — **`file_t`, the descriptor table and syscall dispatch.** `open`/`read`/`close` on NVFS through the real `COP` path.
- [ ] V4 — **ext2 read-only behind the same table** — the same gate as [E2.1](sec_ai_y3#e21). Both filesystems mounted at once, and paths resolving across the mount point.
- [ ] V5 — **The shared block cache and its ordering rule.** The journal invariant holds under the shared cache and the crash-injection suite passes.
  NOTE: V5 may trail V4. ext2 on its own private cache is a valid intermediate state, because the ordering hook exists for NVFS's benefit alone.
