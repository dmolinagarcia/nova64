# Filesystems — NVFS, the native volume
> the on-disk format · the journal · what a crash can leave

NVFS is the filesystem the machine boots from, keeps its kernel and programs on, and will eventually page from. It is designed for this machine and attempts no generality: **recoverable without human intervention** first, then **implementable on a 65816** — every hot-path index a shift or a mask, steady-state RAM in single-digit kilobytes — then **cheap in block transfers**, since transfers dominate and elegance that costs an extra read is a bad trade, then **verifiable**, then faithful to POSIX wherever that is free. Explicitly not goals: compression, encryption, snapshots, quotas, extended attributes, ACLs, multi-device volumes, online resize, big-endian hosts, and any block size but 2048. The layer above is [sheet Y1](sec_y1); the foreign filesystem beside it is [sheet Y3](sec_y3).

- Y2.1 — **Draft 3 is a format break and there is no migration path inside the filesystem.** A draft 2 volume is evacuated by copying its files out with the old tooling, reformatted, and copied back — which makes **archiving and tagging the draft 2 tooling the one action that must happen before any draft 3 code is written**, because step one depends on it and there will be no way to reconstruct it. Draft 3 refuses a draft 2 volume cleanly rather than as generic corruption: the superblock is at a different block and the magic check fails. `mkfs`, `nvfsck` and the 65816 read path are rewritten; the assembly CRC-32 is reusable unchanged; the conformance and crash-injection harnesses survive and their corpora do not.
  NOTE: **The cost is real and is the main argument against the break.** What buys it is five changes, each of which pays on this machine specifically: a journal in place of ordering discipline, a 2048-byte block equal to the MMU page, extents in place of indirect trees, fixed-size directory slots, and POSIX-identical mode bits (→ [D51](sec_q#d51)).
- Y2.2 — **A journal replaces write ordering, and the argument is where the correctness lives.** Ordering discipline is a correctness argument spread across every mutating operation — which is why the crash-injection harness found ordering bugs in draft 2, and why [Y3.9](sec_y3#y39) has to make the same argument again for ext2. A journal is a correctness argument in **one place**. On a machine with no on-target `fsck`, bounded idempotent single-pass recovery is worth what it costs.
- Y2.3 — **The block is 2048 bytes, fixed, and that single number is the source of most of this sheet's arithmetic.** It is exactly one virtual-memory page ([L.1](sec_l#l1)) and exactly four SD sectors. **Demand-paging a page out of an executable is therefore one block read** — worth more than any other optimisation here. And every index conversion becomes a shift on a CPU with no divide and a 16-bit ALU: `lba = partition_lba + (block << 2)`, `itable_block = start + ((ino−1) >> 4)`, `bitmap_block = start + (b >> 14)`. **There is no division anywhere in the NVFS data path.**
  NOTE: `s_block_size` exists in the superblock so that a later version can relax this, and in version 3.0 it MUST be 2048; a volume where it is not is refused at mount rather than worked around.

## Fundamental parameters — the constants every formula above depends on.

| Parameter | Value | Why |
|---|---|---|
| Block size | **2048 B, fixed** | = MMU page · = 4 SD sectors · all index maths become shifts |
| Inode size | **128 B, fixed** | 16 per block; `slot = (ino−1) & 15` |
| Directory slot | **64 B, fixed** | 30 slots per block after the header |
| Maximum name | 56 bytes | fits the slot with no spill mechanism |
| Block and inode numbers | `u32` | same width as the SD LBA; two 16-bit adds |
| File size | `u32` | 4 GiB − 1, against a 16 MB address space |
| Maximum extent | 65,535 blocks | 128 MiB in one entry |
| Maximum extent depth | 3 | sufficient for a maximum-size file of single-block extents |
| Blocks per journal transaction | 507 | the 65816 driver caps itself at 64 ([Y2.17](sec_y2#y217)) |

- Y2.4 — **Conventions, and two of them are load-bearing.** Every multi-byte field is **little-endian**, which matches both the 65816 and every intended host: **no implementation performs a byte swap**, and one that finds itself wanting a swap accessor has a bug elsewhere. Every field is naturally aligned, which the 65816 does not require but which lets a host map structures directly and lets a static assertion catch layout drift. Reserved fields are written zero and **ignored** on read — forward compatibility is governed by the feature flags of [Y2.20](sec_y2#y220) and by nothing else. Names are byte strings, 1 to 56 bytes, no NUL and no `/`, with no encoding, no normalisation and no case folding: **two names differing in any byte are different names.**
  NOTE: **Time is `u32` seconds since 1970 and the board has no source for it.** A host with no reliable wall clock writes **zero**, meaning "unknown", and `nvfsck` must not report zero as an error. That is a hardware gap rather than a filesystem question and it should be closed before the board is frozen (→ [Q88](sec_q#q88)).
  NOTE: **One checksum algorithm appears in this sheet and no other**: CRC-32, reflected, polynomial `0xEDB88320`, init and final XOR `0xFFFFFFFF` — the CRC-32 of IEEE 802.3, zlib and gzip, check value `0xCBF43926`. Every 2048-byte metadata block that carries a block checksum stores it at offset `0x7FC`, computed over the whole block with those four bytes zeroed, so **there is exactly one such routine in any implementation**. The directory name hash is derived from the same pass ([Y2.13](sec_y2#y213)).

## Volume layout — one MBR partition, everything numbered from its first block.

| Region | Extent | Superblock fields |
|---|---|---|
| Reserved, including the primary superblock at block 1 | blocks 0–7, fixed | — |
| Journal superblock + ring | | `s_journal_start` · `s_journal_blocks` |
| Block bitmap | | `s_bitmap_start` · `s_bitmap_blocks` |
| Free-count summary | | `s_summary_start` · `s_summary_blocks` |
| Inode bitmap | | `s_ibitmap_start` · `s_ibitmap_blocks` |
| Inode table | | `s_itable_start` · `s_itable_blocks` |
| Data | `s_first_data_block` … `s_total_blocks − 2` | |
| Backup superblock | last block | `s_backup_sb` |

- Y2.5 — **The order is fixed and `nvfsck` verifies it.** The 8-block reserved area exists so a boot loader can live at the front of the partition without leaving a hole in the filesystem; blocks 0 and 2–7 are never read or written by NVFS itself. Everything from block 0 to `s_first_data_block − 1`, plus the backup superblock, is marked allocated at `mkfs` time, and **bits beyond `s_total_blocks` in the last bitmap block are set to 1 so the allocator can never return an out-of-range block.**
  NOTE: `mkfs` sizing, informative rather than normative: journal ring `clamp(total/64, 256, 8192)`, one inode per 16 KiB, and the bitmap, summary and table lengths that follow. On a 64 MiB volume that is 782 blocks of metadata out of 32,768 — **2.4 %, of which the journal is 1.6 %** — and the journal fraction stays constant as the volume grows, which is the argument for capping it (→ [Q89](sec_q#q89)).
- Y2.6 — **The backup superblock is written by `mkfs` and `nvfsck` and by nothing else.** It records the immutable layout, which never changes; its counters and timestamps are those from format time and are ignored on recovery. **An implementation must not silently fall back to it**: if block 1 fails its magic or CRC, the mount fails, and recovering from the backup is an explicit `nvfsck` operation. `s_partition_lba` in the superblock is informative — the implementation uses the LBA it got from the partition table and warns if the two disagree.
  NOTE: `s_free_blocks` and `s_free_inodes` are advisory, so that `statfs` need not scan the bitmaps, and they are **maintained inside the same transaction as the bitmap change that alters them** so a crash cannot desynchronise them. `nvfsck` recomputes them and corrects silently.
- Y2.7 — **A flat bitmap with a free-count summary in front of it, and no block groups.** Bit *n* is block *n*, 1 means allocated, 16,384 bits per block — which is why the index is a shift. There are no groups because at the volume sizes this machine will see, 8–32 GiB and so 256–1024 bitmap blocks, the locality a group buys does not pay for its bookkeeping. The summary is one `u16` per bitmap block holding its free count, so the allocator skips a full block without reading it; on a 1024-block bitmap the whole summary is one block.
  NOTE: 16,384 does not fit in 16 bits, so **`0xFFFF` encodes it and is reserved for that** — a completely free bitmap block only occurs on a fresh volume and the special case is two instructions, against four times the summary for a `u32`.
  NOTE: **Bitmap and summary blocks carry no checksum, and this is documented debt rather than an oversight.** A 4-byte CRC would leave 16,352 bits per block, which is not a power of two, and `bitmap_block_of()` would become a division by 16,352 in the hottest path in the allocator on a CPU with no divide. The accepted consequence: a torn bitmap block is not detected at mount. It is detected by `nvfsck`, which recomputes the bitmap from the extents — and the journal already guarantees that a bitmap block is only ever written from a CRC-protected transaction. **Revisit it if the block size ever changes.**
- Y2.8 — **Inodes are 1-based, 16 to a block, and identity outlives them.** Inode 1 is the root directory, always allocated and always a directory; 2–7 are reserved and marked allocated with type 0; 8 upward are allocatable. Each new inode takes `i_generation` from a superblock counter, so **the pair (number, generation) uniquely identifies an inode over the life of the volume** — which is what a host binding needs for handle validity and what [Y1.7](sec_y1#y17)'s vnode cache will need if it ever holds a handle across an unlink.
  NOTE: A free inode has `i_mode` and `i_links` zero **and a valid `i_crc32`**, so that a free inode is distinguishable from a corrupt one.
- Y2.9 — **The inode is 128 bytes and `i_mode` is bit-identical to POSIX**, which is what makes [Y1.3](sec_y1#y13)'s translation table unnecessary in both directions. Type nibble: `0x1` FIFO, `0x2` character device, `0x4` directory, `0x6` block device, `0x8` regular, `0xA` symlink; any other value makes the inode invalid. **Bits 11–9 — setuid, setgid, sticky — are reserved and must be zero**: this is a single-user machine, they have no meaning here, and accepting them would create a security surface with no matching benefit. The kernel interprets only the owner triplet; group and other exist so a host binding round-trips and so a multi-user story is not foreclosed.
  NOTE: `i_blocks` counts **NVFS blocks, not 512-byte units** — deliberately unlike ext2, whose 512-byte convention is a well-known source of bugs and which there is no reason to inherit. It counts extent-tree nodes and excludes holes.
  NOTE: Three inode flags are defined and the rest are reserved: `IMMUTABLE`, `APPEND`, and `SYNC` — the last making every mutation on that inode commit its transaction before returning.
  NOTE: **`i_atime` is not maintained on read.** Doing so turns every read into a write, which this machine cannot afford. It is set by `mkfs`, on creation, and on an explicit `utimes`; the format supports relative-atime behaviour and nothing here depends on it.

## Inode — 128 bytes, the fields that matter.

| Offset | Field | Meaning |
|---|---|---|
| `0x00` | `i_mode` · `i_links` | POSIX type and permissions · hard link count, 0 = free or orphaned |
| `0x04` | `i_size` · `i_blocks` | bytes · NVFS blocks charged to the file |
| `0x0C` | `i_mtime` · `i_ctime` · `i_atime` | |
| `0x18` | `i_generation` | [Y2.8](sec_y2#y28) |
| `0x1C` | `i_flags` · `i_ext_count` · `i_ext_depth` | flags · valid entries in `i_ext[]`, 0–6 · tree depth, 0–3 |
| `0x20` | `i_ext[6]` | six 12-byte extent entries — 72 bytes, also the inline symlink area |
| `0x68` | `i_uid` · `i_gid` · `i_rdev` | preserved, never enforced · device number or 0 |
| `0x70` | `i_orphan_next` · `i_dirhash_order` | [Y2.19](sec_y2#y219) · [Y2.14](sec_y2#y214) |
| `0x7C` | `i_crc32` | over bytes `0x00`–`0x7B` |

- Y2.10 — **Extents, not an indirect tree, because at ~2.5 ms per block transfer an indirect read is a visible cost.** A leaf entry is 12 bytes — logical block, physical block, length in blocks, flags — and an index entry is the same shape pointing at a child node. The root is the inode's six entries; a node is 2048 bytes holding **exactly 169 entries**, since `0x010 + 169 × 12 = 0x7FC` leaves precisely the checksum. Depth 0 gives 6 extents, depth 1 gives 1,014, depth 2 gives 171,366 and **depth 3 gives 28,960,854 — enough for a maximum-size file in which every extent is a single block**, so depth 3 is the cap and it is sufficient by construction.
  NOTE: **A logical block covered by no extent is a hole**, read as zeros. Holes are the absence of coverage and never a special extent value. Entries at every level are sorted ascending and must not overlap, which is what makes lookup a search and lets `nvfsck` validate a tree in one pass.
  NOTE: **The lookup's structural check is mandatory, not advisory: a child's depth must equal its parent's minus one.** That is what stops a corrupted index pointer from causing an unbounded walk, and combined with the depth cap it bounds the walk by construction.
  NOTE: **Merging on insert is required and merging on delete is not.** An implementation must merge an extent with its predecessor when they are contiguous in both spaces with identical flags and the result fits — without it, sequential writes produce one extent per block and defeat the entire design. A tree left sparse by truncation is acceptable and `nvfsck` must not report it.
  NOTE: `UNWRITTEN` marks preallocated space: charged to the file, unavailable to anything else, contents undefined, **read as zeros**. Writing into one splits it. A 3.0 implementation need not create them but **must handle them on read**, because the host library creates them for `fallocate`.
- Y2.11 — **A symlink whose target is 72 bytes or shorter is stored inline in the extent area**, with no extents and no blocks charged, and it is detected purely by the size — **no flag bit is needed and none is defined.** Longer targets are ordinary file data. Directories are files whose size is always a whole number of blocks and which may contain **no holes**.
- Y2.12 — **Directory slots are fixed at 64 bytes, and this is the change that removes a whole class of corruption.** Variable-length records with an in-band length field are the single largest source of directory corruption in ext2-class filesystems: one bad length desynchronises a block, and [Y3.10](sec_y3#y310) has to spend sanity checks defending against exactly that. Here there is no length-linked chain: a slot holds inode number, a 16-bit name hash, name length, type, and 56 name bytes. **A free slot is one whose inode number is zero**, deletion is a single-field write followed by zeroing the rest, and slots within a block are unordered. Thirty slots fit a block after its header.
  NOTE: The hash is the low 16 bits of the same CRC-32, and it exists so that **a lookup compares two bytes before it compares up to 56**. It is a fast reject only: a match must still be confirmed against the length and the bytes.
  NOTE: The type byte matches the Linux `DT_*` constants so a host binding passes it through, and it **must agree with the target inode's type nibble**; `nvfsck` reports a disagreement and repairs it from the inode, which is authoritative.
- Y2.13 — **Neither `.` nor `..` occupies a slot; both are synthesised.** `.` is the directory itself, and **the parent inode number is not stored — it is supplied by the caller**, which necessarily knows it because that is how it reached the directory. This removes two slots per directory and, far more importantly, removes the `..` link-count bookkeeping that is a persistent source of `fsck` errors.
  NOTE: The cost is stated rather than hidden: a directory found by inode number alone has no path back to its parent, so `nvfsck` reconstructs parenthood by full traversal — which it does anyway. **And a directory's link count is therefore always exactly 2**, one for its entry in the parent and one for itself, with subdirectories *not* incrementing the parent. That differs from the POSIX convention of 2 + subdirectories, so a host binding must synthesise the POSIX value if any tool depends on it. There are 8 reserved bytes in the inode if a stored parent is ever wanted instead (→ [Q93](sec_q#q93)).
- Y2.14 — **Lookup is a linear scan and the cost is stated honestly: one block read per 30 entries, so a 300-entry directory is 10 reads, about 25 ms.** Insertion takes the first free slot in the first block with room, or appends a block. Deletion never frees a block and never shrinks the directory — **a directory shrinks only when it is removed.** The `readdir` cookie is `block × 30 + slot + 1`, with 0 meaning start, stable for the directory's lifetime as long as no block is added.
  NOTE: **`DIRHASH` is defined so that it can be added later without a format change, and is not required in 3.0** — `mkfs` must not set the bit by default, and the recommendation is to ship linear-only. When enabled, a directory's blocks become 2^order buckets selected by the *upper* 16 bits of the same CRC whose lower 16 are the slot hash, so **one CRC pass still serves both**. Growth is a bulk rebuild rather than incremental splitting, because a rebuild is easier to make crash-safe and easier to verify, and directories large enough to need it are rare here.

- Y2.15 — **The journal is physical, redo-only, metadata-only and circular**, and three properties follow that are the entire reason for that shape. **Replay is idempotent** — it copies whole blocks to fixed destinations, so running it twice equals running it once and a crash *during* recovery is harmless. **Replay is order-only** — no undo, no dependency graph, no compensating records, so recovery is a forward scan and a sequence of block copies, a few hundred bytes of 65816 code. And **a transaction needs one block of RAM**: metadata blocks are streamed into the journal as they are modified rather than buffered, and a block logged twice in one transaction is simply logged twice, with the later copy winning at replay.
  NOTE: **File data is never journaled**, and [Y2.18](sec_y2#y218) is the ordering rule that replaces it.
  NOTE: **There is no escape mechanism and none is needed**, unlike ext3. Recovery never has to guess where a block boundary falls: the descriptor states the count, recovery reads exactly that many blocks and expects the commit block at a computed position, and it **never interprets a logged block**. The scan for the next descriptor resumes arithmetically, never by searching for a magic. Which is why the count is validated against 507 *before* it is used, and why an out-of-range count terminates recovery rather than being skipped.
- Y2.16 — **Commit is seven steps that must not be reordered, and a checkpoint that may be deferred.** Log each modified metadata block into the ring, recording its home destination; **ensure every file data block this transaction wrote is durable**; write the descriptor; barrier; write the commit block carrying a CRC over the descriptor and all logged blocks; barrier — **the transaction is durable here**. Then checkpoint: write each logged block to its home, barrier, advance the journal superblock's checkpoint and sequence, barrier. The last three may be batched across several transactions.
  NOTE: Recovery is the mirror and stops at the first thing that does not check out: a bad descriptor magic, CRC, sequence or count; a bad commit block; a payload CRC that disagrees. **Destinations are validated before use** — in range and outside the journal region — and a violation aborts recovery and fails the mount. Entries are applied in ascending order, because that is what makes the later copy of a twice-logged block win. **The checkpoint is advanced only after the replayed blocks are durable**: advancing it first is the one way to lose data in this design.
  NOTE: "Barrier" means every write issued before it is durable before any issued after. On SD that means waiting for the card to leave busy and confirming with `CMD13` — and **whether that is actually a durability guarantee is an open assumption, not a fact** (→ [Q96](sec_q#q96)).
- Y2.17 — **A freed block may not be reused until the transaction that freed it is checkpointed.** Without that rule a replay can write stale metadata over freshly written file data. ext3 solves the same problem with revoke records; those were considered and rejected, because they add a second record type, a second scan pass and a hash table to recovery — all in the one piece of code that must stay under a few hundred bytes on the 65816. The implementation is a small in-memory set cleared at every checkpoint, and an implementation may simply refuse to reuse *any* freed block until the next checkpoint at the cost of some transient under-reporting.
  NOTE: A transaction that does not fit the free ring forces a checkpoint until it does. **The 65816 driver caps transactions at 64 blocks**, which bounds the in-RAM destination array to 256 bytes; a single transaction larger than the ring is a bug, and the general cap is `min(507, ring/2)`.
- Y2.18 — **One rule governs data, and it is `data=ordered`: every file data block a transaction wrote must be durable before that transaction's commit block is written.** This guarantees that metadata never references a block whose contents are stale — that **a crash can never expose the previous occupant of a reallocated block through a newly written file**. `data=writeback` would be faster and is not permitted: on a single-user machine with no other protection, stale-data exposure is both a correctness and a privacy failure. If the barrier per transaction proves intolerable, the alternative is journaling small writes with the metadata, not relaxing this (→ [Q97](sec_q#q97)).
  NOTE: **The complete list of post-crash states is three, and there is no fourth.** Not committed: nothing of it is visible, its data blocks are unreferenced and their bits are clear — no leak. Committed, not checkpointed: replayed, fully visible. Committed and checkpointed but the checkpoint not advanced: replayed again, idempotently, fully visible. In particular **there is no state in which a directory entry points at a free inode, or a bitmap bit disagrees with an extent**, because those pairs are never split across transactions.
  NOTE: `fsync` flushes the file's data, commits the transaction holding its metadata, and returns — it need not checkpoint. **`fsync` on a directory commits that directory's modifications**, which is what makes "create a file, fsync the directory" durable, and the layer above must expose it ([Y1.20](sec_y1#y120)).

## Transaction atomicity — the normative checklist the crash-injection harness tests against.

| Operation | What must commit together |
|---|---|
| Block allocate / free | bitmap block · summary entry · superblock counters · the metadata block that now does or no longer does reference it |
| Inode allocate | inode bitmap · inode table block · superblock counters |
| Create | the inode-allocation group · the directory block · the directory inode · any new directory block's allocation |
| Unlink | directory block · target inode's link count · orphan-list insertion if it reaches zero |
| Link | directory block · target inode |
| Rename | both directory blocks · both directory inodes · the replaced target inode if any |
| Write extending a file | inode · every modified extent node · an allocation group per new block |
| Truncate | inode · every modified extent node · a free group per released block |
| Directory grow | directory inode · the new directory block · the extent change · the allocation group |

  NOTE: A `rename` spanning two directory blocks is the largest common transaction and fits the 64-block cap comfortably.

- Y2.19 — **The one thing a crash can leak is an orphan, and the orphan list is what collects it.** An inode whose link count reached zero while it was still open is threaded onto a list headed in the superblock — inserted in the same transaction as the final `unlink`, removed and freed when the last handle closes. **At mount, after recovery, the list is walked and every inode on it freed.** That is the mechanism that keeps crashes from leaking space, and it is why NVFS needs no on-target `fsck` for the common case.
  NOTE: The walk **bounds itself**: it stops after `s_total_inodes` steps and rejects an out-of-range inode number. A cycle is corruption and fails the mount rather than looping.
- Y2.20 — **Three feature masks, and the policy is enforced at mount before any other validation.** An unknown `incompat` bit refuses the mount; an unknown `ro_compat` bit mounts read-only; an unknown `compat` bit is ignored. **The implementation must name the bit it did not recognise** — a mount failure that says only "unsupported features" is not acceptable, and this is the single most useful diagnostic a filesystem can emit.
  NOTE: The two `ro_compat` bits defined — metadata checksums present, journal present — are **always set in 3.0**, and putting them in the read-only mask rather than the incompatible one is deliberate: a minimal read-only reader, a boot loader for instance, that neither verifies checksums nor replays the journal can still mount a **cleanly unmounted** volume. One that meets a dirty state or a non-empty journal must refuse. `DIRHASH` is the only `incompat` bit defined.
- Y2.21 — **Mount is eight steps and the order is the safety.** Locate the partition; read block 1 and verify magic and CRC; check version and block size; **apply the feature policy**; sanity-check the layout — every region in range, correctly ordered, non-overlapping; read the journal superblock and run recovery; if read-write, walk and free the orphan list, then mark the volume dirty and count the mount; finally read inode 1 and verify it is a directory. A volume in the error state mounts read-only and reports that `nvfsck` is required.
- Y2.22 — **`nvfsck` is host-side, there is no on-target `fsck`, and none is planned.** In a single pass it must verify the superblock and its agreement with the backup on immutable fields; the journal's validity and **emptiness**, replaying first or refusing; every inode's CRC, type and flags; every extent tree's magic, CRC, back-reference, depth consistency, sorted non-overlapping entries and in-range physical blocks; **a reconstructed block bitmap against the stored one**; a reconstructed inode bitmap and per-inode link count; every directory block's magic, CRC, back-reference, used count, name lengths, hashes and types, with no duplicates; **full connectivity from the root**, no cycles, no directory with two parents; the orphan list; and the advisory counters. Counters and bitmap leaks are repaired silently; everything else asks.
  NOTE: The severity ordering in the bitmap check is the part worth remembering: **allocated but referenced by nothing is a leak and correctable; referenced by two inodes is a cross-link and serious; referenced but marked free is the fatal case.**
- Y2.23 — **Steady-state RAM for a single-mount, single-open-file driver is about 4.7 KiB**: two 2048-byte buffers, one for metadata and one for data, a 256-byte journal destination array, a 128-byte inode working copy, 64 bytes of cached layout constants — **not the whole superblock block** — and scratch for a name and a path component. That fits comfortably in the kernel's bank `$01` allocation ([J.1](sec_j#j1)). A second data buffer doubles sequential throughput for 2 KiB and is an implementation choice, not a format requirement.
  NOTE: **The 2048-byte buffers must not straddle a 64 KB bank boundary.** Aligning each to 2048 satisfies that automatically and also makes the SD destination address trivially computable ([G.8](sec_g#g8)). The same rule holds for ext2 ([Y3.12](sec_y3#y312)).
  NOTE: Under Calypsi, `int` is 16 bits: every on-disk field and every counter that can exceed 65,535 takes an explicit fixed-width type, and block and inode arithmetic is two 16-bit operations. **A static assertion on every structure size must be present in both the host and the Calypsi build** — a structure that silently gains padding on one of the two is exactly the bug that produces a volume readable by one implementation and not the other ([O.2](sec_o#o2)).

## Cost model — budget targets extrapolated from ~8–10 K cycles per KiB at 8 MHz, **not measurements**. They must be measured on real hardware before this format is frozen.

| | Blocks | Estimate |
|---|---|---|
| One block transfer | 1 | ≈ 2.5 ms |
| Clean mount | 3 | ≈ 8 ms |
| Path lookup, two components, small directories | 4 | ≈ 10 ms |
| **Demand-page one 2 KiB page of an open executable** | **1** | **≈ 2.5 ms** |
| Create a file in a directory with a free slot | ≈ 13 | ≈ 33 ms |
| Sequential write of 64 KiB into one extent | ≈ 44 | ≈ 110 ms · ≈ 580 KiB/s |

  NOTE: **The journal roughly doubles metadata write cost.** For unpacking an archive that is a real slowdown; for bulk data it is negligible, because data is not journaled. Batching several operations into one commit recovers most of it, and the driver should do so with an interval of about a second plus an immediate commit on `fsync`.

- Y2.24 — **What this sheet needs from [sheet G](sec_g)'s register map is one sentence, and it is on the critical path.** The natural transfer unit is **four consecutive 512-byte sectors into a 2048-byte-aligned buffer**, and the map should support issuing that as a single multi-block command with one burst into SDRAM rather than four single-sector transfers. Four transfers with per-command overhead is measurably worse than one burst, and the difference multiplies through every figure above. **It is much cheaper to design in now than to add later**, and it is the same request [Y3.12](sec_y3#y312) makes without a number attached (→ [Q22](sec_q#q22), [G.7](sec_g#g7)).
- Y2.25 — **The volume lives in an MBR primary partition of type `0x7F`, and the partition must start at an LBA that is a multiple of 4.** The type byte is the one reserved for local and experimental use by the Alternative OS Development Partition Standard; **`0x7A` and `0x7B`, which an earlier draft proposed, are not safe** — they are the hidden-variant aliases of FAT16 LBA and FAT16B under the +`0x10` hidden-FAT convention, so some host tools will silently treat an NVFS partition as a hidden FAT. GPT is not supported. `mkfs` **refuses** an unaligned partition rather than working around it, because working around it turns every block transfer into two, and refuses volumes below 4096 blocks (8 MiB).
  NOTE: NVFS makes no attempt at wear levelling or erase-block alignment and issues no discard — an SD card contains a flash translation layer that does both (→ [D52](sec_q#d52)).

## Magic number registry — the prefix `NV` is reserved at offset 0 of any metadata block. Bitmap, summary, inode-table and data blocks carry no magic.

| Magic | Structure | Magic | Structure |
|---|---|---|---|
