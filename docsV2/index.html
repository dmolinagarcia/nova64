A

Vision and philosophy

what it is · what for · under what rulesSHEET 01

Project framework: what is being built, what finishing it means, and what principles govern every decision.

  1. A.1
    What it is: an original portable personal computer built around the W65C816S, designed from scratch as a learning exercise in electronics, PCB design, gateware, computer architecture, and OS design.
  2. A.2
    Inspiration and goals: two milestones define success. Apple II Milestone — the machine boots on its own to a prompt. Amiga Milestone — preemptive multitasking with a windowed GUI.
  3. A.3
    Non-negotiable principles: every component hand-solderable (TQFP / PLCC / TSOP / 0.5 mm max.), everything at 3.3V, open toolchain (KiCad · Yosys · nextpnr · IceStorm · pico-sdk), incremental progress with an explicit verification criterion per stage, and unpopulated footprints to preserve future expansion.
  4. A.4
    Scope of this document: an index + outline tying all the pieces together. Detail lives in the sheets: hoja-1-1-alimentacion.md … hoja-1-6-conectores.md, hoja-pines-ice40.md, plan-implementacion-65816.md and the diagram placa-65816.html (REV B).
B

Global architecture

physical CPU + optional softcore · A = northbridge · B = video/audioSHEET 02

An Amiga-style shared bus with four inhabitants: the physical CPU, two always-present FPGAs, and an optional third one. The RP2040 stays off the bus, acting as the board controller.

  1. B.1
    CPU: W65C816S in a PLCC-44 socket, 24-bit native mode. PHI2 generated by FPGA-A (target 8 MHz at 3.3V). The BE signal lets the CPU release the bus.
  2. B.2
    FPGA-A — the "northbridge": MMU + TLB + walker, cache, bus arbiter, prioritized interrupt controller, system timer, UART, SPI-SD, I2C, and CPU glue logic. iCE40HX4K/HX8K TQ144 · budget: ~93/107 pins used.
  3. B.3
    FPGA-B — video and audio: taps the bus directly; the CPU writes to it through a 64 KB VRAM window in bank $FE, validated by the MMU's VRAM_SEL signal. Its own 8 MB PSRAM (chip RAM), RGB-TTL output to the panel, bring-up VGA, and PCM5102A over I2S.
  4. B.4
    FPGA-C — optional, unpopulated at first: a 65816 softcore (P65816 reference) that takes the same bus with BE=0. Allows switching from the real CPU to a softcore without touching the rest.
  5. B.5
    RP2040 — embedded controller off the bus: configures, boots, and watches over the system (→ sheet D). The board's only mandatory flash: its W25Q16.
  6. B.6
    Interconnect: a single shared A/D/control bus; no dedicated links between FPGAs (removed). The microSD is shared between the RP2040 and FPGA-A via a '3257 mux (→ sheet F).
C

Power supply

battery · charger · power-path · state measurementSHEET 03

1S chain with power-path: the machine runs on USB even with the battery depleted or absent, and the RP2040 governs the full sequencing. Detail in hoja-1-1-alimentacion.md.

  1. C.1
    Input: USB-C sink — 5.1 kΩ CC resistors + ESD protection.
  2. C.2
    MCP73871: 1S Li-Ion charger with power-path → SYS node. Charging and system consumption are shared without interruption.
  3. C.3
    Battery: 1S Li-Ion 3000 mAh (estimated runtime >10 h). State measurement: MAX17048 (fuel gauge, I2C) read by the EC; the RP2040 can perform an orderly shutdown on critical battery even if the OS is hung.
  4. C.4
    SYS → TPS63020 buck-boost → 3V3 always-on rail (RP2040 and logic).
  5. C.5
    Rails derived from 3V3: 1.2V LDO with EN for the iCE40 cores · VCCPLL filtered per FPGA · VPP 2.5V via BAT54 from 3V3 (avoids a dedicated rail) · panel load switch.
  6. C.6
    Boosts hanging off SYS (not VBAT): PT4110 for the LED backlight (~1.5W reserved; brightness EN/PWM from the RP2040) and TPS61023 → 5V VBUS for the USB-A host port (500 mA, EN on demand). LED string current/voltage: pending the module datasheet (→ N).
  7. C.7
    Safe bring-up: 0Ω jumpers per rail to isolate and measure each block in stage E1.
  8. C.8
    Sequencing governed by the RP2040: CRESET_B held until rails are stable; panel and host VBUS off by default. PCF8563 (RTC) shares the I2C bus with the fuel gauge.
D

RP2040 — embedded controller

boot · FPGA programming · console · ECSHEET 04

It's the laptop's "management microcontroller": it handles everything that happens before a live CPU exists, and stays on watch afterward. Detail in hoja-1-2-rp2040.md and hoja-1-3-config-fpga.md.

  1. D.1
    Triple role: programmer (bitstreams, BIOS, its own firmware — all over USB), bootstrapper (full sequence in Fig. 3), and permanent embedded controller. Its W25Q16 is the board's only mandatory flash.
  2. D.2
    9-step boot (Fig. 3): button → rails → SSPI configuration of FPGA-A/B(/C) with CRESET_B/CDONE → SDRAM initialized by gateware → BIOS from SD to SRAM → SD handoff → RESB↑ → $FFFC vector.
  3. D.3
    Debugging: a debug port into FPGA-A — live read/write of system memory, a free "ICE" for the kernel.
  4. D.4
    Console: USB-CDC ↔ FPGA-A UART. It's the terminal for the monitor (E2) and the OS until there's a screen of its own.
  5. D.5
    HID host: PIO-USB + hub — USB keyboard and mouse (PS/2 and matrix removed). Powers up the TPS61023 on demand and translates HID → events to the kernel over the EC channel.
  6. D.6
    EC in operation: power button, MAX17048 readout, RTC, safe shutdown with the OS hung. open EC↔kernel protocol yet to be defined (→ N).
E

Physical memory structure

how CPU · FPGA-A · SRAM · SDRAM relateSHEET 05

All system memory lives behind FPGA-A: the CPU never sees SRAM or SDRAM directly, only virtual addresses translated by the MMU and served by the cache.

  1. E.1
    Hierarchy: registers → cache in SRAM → SDRAM (physical frames) → microSD (swap, post-v1).
  2. E.2
    2 MB SRAM (IS61WV102416, 10 ns), unified: 1 MB cache (256 B lines) + 512 KB page tables + 512 KB pinned for the per-process $00 bank and the kernel. Replaces the external table SRAM, removed due to pin budget.
  3. E.3
    32 MB SDRAM (W9825G6KH, TSOP-II 54, 3.3V): main memory — 16,384 2 KB frames. Target controller ~50 MHz; open-source candidates: lawrie/blackicemx, niklasnisbeth/ice40-litedram, ZipCPU/zipstormmx.
  4. E.4
    SRAM and SDRAM share a 16-bit bus behind FPGA-A: line fill is serialized (SDRAM→FPGA burst, then FPGA→SRAM), but a cache miss stays at ~200–300 ns — well below the QSPI it replaces.
  5. E.5
    8 MB APS6404L PSRAM on FPGA-B = chip RAM (framebuffer + audio DMA buffers), outside the CPU hierarchy; reached through the $FE window.
  6. E.6
    Architectural ceiling: 128 MB physical (16-bit frame in the PTE) — headroom for future revisions without touching the format.
  7. E.7
    Layout note: SRAM + SDRAM in a short comb, hugging FPGA-A — the bus runs at ~100 MHz and won't tolerate long stubs.
F

Persistent storage — microSD

where it connects · boot · normal useSHEET 06

A single slot, two owners at different times. It's also the only boot path: the dedicated BIOS flash was removed from the design.

  1. F.1
    Connection: the slot hangs off an SN74CBTLV3257 mux between the RP2040 and FPGA-A's SPI-SD controller, with a handoff handshake.
  2. F.2
    At boot: the RP2040 owns the SD — it reads BIOS.BIN from FAT and preloads it into the pinned SRAM zone (steps 5–6 of Fig. 3). It then switches the mux to FPGA-A before releasing reset.
  3. F.3
    In normal use: the 65816 accesses it through FPGA-A's SPI-SD via the kernel's block driver. The BIOS mounts FAT read-only to load KERNEL.BIN; the OS adds write support and the user filesystem.
  4. F.4
    Card contents: /BIOS.BIN · /KERNEL.BIN · user tree (programs, data) · future reserve for swap.
  5. F.5
    Recovery: the RP2040 can reclaim the SD over USB at any time — update BIOS/kernel without removing the card.

H

BIOS — what it provides

residency · services · boundary with the ECSHEET 08

There's no BIOS chip: it's a binary on the SD that the RP2040 preloads into SRAM. The 65816 comes to life with the $FFFC vector pointing inside that zone.

  1. H.1
    Residency: BIOS.BIN on the SD → preloaded by the RP2040 into the pinned SRAM zone (step 5 of Fig. 3). No dedicated flash.
  2. H.2
    At reset it provides: CPU init (native mode CLC/XCE, stack, direct page), MMU in supervisor identity mapping, cache init, quick memory test, UART console, and boot screen.
  3. H.3
    Machine monitor: peek/poke, dumps, serial loading — the working tool for stages E2–E4.
  4. H.4
    OS loader: mounts FAT (read-only), locates KERNEL.BIN, loads it, and jumps to it passing an info block: RAM size, device map, battery state, and RTC time (via EC). open Exact block format yet to be finalized (→ N).
  5. H.5
    Residual services to the OS: a small JSL jump table (putchar, getchar, read sector) during the transition; once the kernel drivers take over, the BIOS stops being used.
  6. H.6
    Boundary of responsibilities: the RP2040 is the "board BIOS" (everything pre-CPU); this binary is the "system BIOS" (everything post-reset). Together they cover what a single firmware does in a PC.
I

Operating system

how it uses the BIOS · what it provides to processesSHEET 09

Small monolithic kernel, written in C with assembly only where it hurts. It consumes the BIOS for a few milliseconds and then provides everything else.

  1. I.1
    Model: preemptive kernel resident in virtual bank $01 (64 KB, pinned in SRAM), mapped identically and privileged in every process's page table.
  2. I.2
    How it uses the BIOS: only the info block and the JSL table during the transition; its drivers replace the console and SD, and from then on the BIOS goes inert.
  3. I.3
    What it provides — syscalls via COP (the signature byte is the service number), Unix-style table: proc exec · exit · wait · yield · sleep · kill / mem sbrk · mmap · munmap · mshare / unified I/O open · close · read · write · seek · stat · ioctl.
  4. I.4
    Internal drivers with a fixed 5-function interface — init · read · write · ioctl · irq_handler — exposed as /dev/*. Swapping a chip = reimplementing the interface without breaking the user ABI.
  5. I.5
    Framebuffer: the preferred path is an ioctl that maps VRAM pages ($FE) into the process's address space — no per-pixel write().
  6. I.6
    Filesystem: FAT over the SD + minimal devfs. Per-device blocking queues and basic IPC. sketch
J

Virtual memory management

full paging · TLB · walker · ABORTSHEET 10

Every process sees a clean, contiguous 16 MB; FPGA-A's MMU does the rest. The 65816's ABORTB pin turns this into real memory protection.

  1. J.1
    Virtual space: 16 MB per process (24-bit), full paging with 2 KB pages → 8,192 pages (13-bit page + 11-bit offset). Page size is decoupled from the cache line (256 B).
  2. J.2
    Flat table: 8,192 PTEs × 32 bits = 32 KB per process. The 512 KB region in SRAM holds up to 16 resident tables; inactive ones can live in the kernel's pageable memory.
  3. J.3
    32-bit PTE (finalized format): FRAME[15:0] + P · W · X · U · D · A · NC · PIN + SW[7:0]. 27-bit physical address → 128 MB ceiling.
  4. J.4
    TLB: 32–64 entries in EBR (the iCE40's 128 Kbit isn't enough for full on-chip tables), tagged by ASID → no flush on context switch.
  5. J.5
    TLB miss → hardware walker (~4 cycles with 10 ns SRAM). Violation or missing page → ABORTB with exact instruction retry; VPA validates X permission; VPB marks privilege transitions.
  6. J.6
    The kernel reads the fault in bank $FF registers: FAULT_ADDR · FAULT_CAUSE · CONTEXT · MODE.
  7. J.7
    Virtual bank map: $00 per-process stack + DP plus a minimal privileged zone (vectors, trampolines, kernel stack — a 65816 requirement: PBR=0 on interrupt entry) · $01 kernel · $02–$FD user · $FE VRAM window · $FF privileged I/O, not mappable to user space — the self-protecting key of the scheme.
  8. J.8
    Physical allocator: frame bitmap over the SDRAM (16,384 × 2 KB). PIN marks non-evictable frames; NC marks uncached zones (I/O).
  9. J.9
    ABORT handler: legitimate heap/stack growth → allocate a frame and retry; anything else → kill the process. v1 uses eager loading; demand paging and swap to SD are post-v1 (with dirty line flush before evicting a page).
K

Process management

PCB · context switch · scheduler · binary formatSHEET 11

The piece that turns the machine into "an Amiga": several isolated processes taking turns without knowing it, with the MMU eliminating relocation at the root.

  1. K.1
    PCB per process: registers (A · X · Y · S · D · DBR · PBR · P · PC), ASID, pointer to its page table, state, and queues.
  2. K.2
    Context switch: save state to the PCB → write CONTEXT/ASID to the MMU → restore the next one. Tens of µs; no TLB flush thanks to ASID.
  3. K.3
    Scheduler: preemptive round-robin with a 100 Hz timer tick; per-device blocked queues; 2–3 priority levels as a later option.
  4. K.4
    Custom binary format: header (magic, entry point) + segments with vaddr · filesz · memsz · R/W/X permissions.
  5. K.5
    Loading (exec): create the page table, map segments with their PTE permissions, zero BSS, map the stack, and RTI to the entry point. Every process sees the same addresses: the MMU makes relocation unnecessary.
  6. K.6
    Lifecycle: exec → ready → running ⇄ blocked → zombie → wait. Isolation is demonstrated in E7: one process dies and the other keeps running.
L

Programming and toolchain

assembly first · C where it's already possibleSHEET 12

Honest assessment of the 65816 ecosystem: boot will be assembly-first, with C coming in as soon as the kernel has firm footing.

  1. L.1
    Assemblers: ca65 (cc65 suite) and 64tass — the base for the BIOS, monitor, and kernel boot.
  2. L.2
    C compilers: WDCTools and LCC-816 as the best options; Calypsi recommendable (C99, large model, 24-bit pointers, JSL/RTL). Ruled out: cc65 (6502/65C02 only) and llvm-mos (llvm-65816 experimental, unusable).
  3. L.3
    Recommended hybrid memory model: code in large model (JSL/RTL) + data with fixed DBR — avoids paying for 24-bit pointers on every memory access.
  4. L.4
    Kernel: C with assembly only in vectors, context switch, critical MMU/cache routines, and boot (~hundreds of lines of asm total).
  5. L.5
    libc: three-line syscall stubs — COP #SYS_n + RTL — invoked with a normal JSL by the compiler.
  6. L.6
    Development flow: compile on the PC (Makefile) → custom binary → transfer over USB (RP2040) or SD → run; debug via serial console + FPGA-A debug port.
  7. L.7
    Gateware: Verilog or VHDL (decision pending, it constrains the P65816 reference softcore) with Yosys + nextpnr-ice40 + IceStorm; simulation always before the board.

Decision log · open questions

what was decided, why · what's left to closeSHEET 14

The decisions shaping the current design, with their reasoning in one line — and the honest list of what's still open.

  1. D01
    ECP5 → 3× iCE40 TQ144 — BGA isn't hand-solderable; 0.5mm TQFP is. Accepted consequence: 128 Kbit EBR → HW walker + small TLB instead of on-chip tables.
  2. D02
    Main PSRAM removed; the 32 MB SDRAM is the memory — the QSPI gateware (the trickiest part) disappears, and a cache miss drops from ~µs to ~200–300 ns.
  3. D03
    External table SRAM removed; a single 2 MB SRAM (cache + tables + pinned) — ~35 pins that didn't fit in the TQ144.
  4. D04
    Amiga-style shared bus; out goes the dedicated FPGA-to-FPGA link and the eDP bridge — FPGA-B taps the bus with the $FE window.
  5. D05
    Direct RGB-TTL 10.1” panel (ER-TFT101-1) — no bridge chip, no NDA (RTD2556 ruled out due to Realtek firmware). eDP/ANX6345 remains a future variant.
  6. D06
    512×300 → 1024×600 px-doubling — the framebuffer fits within the video PSRAM's budget and its QSPI bandwidth.
  7. D07
    USB-only HID (RP2040's PIO-USB) — out go PS/2 and keyboard matrix. Capacitive GT911 touch: the resistive option needed 4 ADCs the RP2040 doesn't have free.
  8. D08
    SD as the only boot path; dedicated BIOS flash removed — incompatible with the pin budget after adding the SDRAM.
  9. D09
    Boosts (backlight, host VBUS) hanging off SYS, not VBAT — the machine runs on USB with the battery depleted. VPP 2.5V via BAT54: out goes the dedicated rail.
  10. D10
    Full 2 KB paging per process (out goes the "one bank per process" model) — a tractable 32 KB flat table, decoupled from the 256 B cache line (which sets tCEM, not the page).
  11. D11
    Hardware walker instead of a software trap on TLB miss — with 10 ns SRAM it costs ~4 cycles and simplifies the kernel.
  12. D12
    32-bit PTE with a 16-bit frame from day one — 128 MB ceiling with no format migrations.

Open questions

  1. Q1
    blocking ER-TFT101-1 module datasheet: backlight current/voltage, strap exposure on the FPC, GT911 connector. Order the panel in the capacitive variant. Blocks the KiCad schematic for sheets 1.5/1.6.
  2. Q2
    HDL choice (Verilog vs VHDL) — constrains the reference softcore (P65816 is VHDL).
  3. Q3
    Specific SDRAM controller among the three open-source candidates (adaptation and verification in E3).
  4. Q4
    EC↔kernel protocol: transport and event format for HID, battery, RTC, and shutdown.
  5. Q5
    Exact format of the BIOS → kernel info block.
  6. Q6
    Backlight brightness control: PWM from the RP2040 (simpler) or from FPGA-B.
